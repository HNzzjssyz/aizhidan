🔧板块一：拼音模块改造

当前拼音数据存储在 localStorage 中，存在容量限制（5MB）、无法跨设备共享、数据易丢失等问题。需要改造为建表存储，并完善增量更新机制。

⚠️ 现状问题：localStorage 容量上限约 5MB，客户+产品数据量增大后容易溢出；数据仅存于当前浏览器，无法跨设备/跨用户共享；增量更新依赖 amstamp/modstm 字段，但未使用 deflag 标记删除记录，可能导致已删除数据仍残留在本地。

1.1 将 localStorage 替换为建表存储

1.1.1 设计数据库表结构 高优先 待开发

将当前 localStorage 的 6 个 key 转化为数据库表：

1.2 添加 deflag 删除标记参数

1.2.1 API 请求添加 deflag 参数 高优先 待开发

当前全量/增量获取请求中没有 deflag 参数，无法识别已删除的记录。需要：

  1. 在全量获取参数中添加 deflag 字段，用于过滤已删除记录： 
    // 客户请求
{ cmd: 'load_data', dtname: 'customer', field: 'id,cu_name,amstamp,deflag', flag: 1 }

// 产品请求
{ cmd: 'load_data', dtname: 'product', field: 'id,pro_name,model,spec,modstm,deflag', flag: 1 }
  2. 在增量获取参数中同样添加 deflag 字段
  3. 前端处理逻辑：
    • deflag = 0（或空值）：正常记录，写入/更新本地
    • deflag = 1（或非零值）：已删除记录，从本地数据库中删除对应记录
🔴 关键：增量更新时必须处理 deflag=1 的记录，否则本地会出现"幽灵数据"——后台已删除的产品仍然出现在匹配结果中。
1.2.2 增量更新时同步删除 deflag=1 的记录 高优先 待开发

增量获取返回的数据中，需根据 deflag 值区分处理：

增量返回数据.forEach(function(record) {
  if (record.deflag == 1) {
    // 从本地数据库删除该记录
    deleteFromLocalDB(record.id);
  } else {
    // 更新或插入该记录
    upsertToLocalDB(record);
  }
});

同时需要删除对应的拼音索引数据。

依赖: 1.1.2 依赖: 1.2.1

1.3 精准落实增量更新

1.3.1 修正增量时间戳逻辑 高优先 待开发

当前增量更新存在以下问题：

  • 时间戳精度问题：使用 new Date().toISOString() 生成时间戳，但服务器数据库的时间可能与客户端不同步
  • 严格大于遗漏：WHERE amstamp > 'lastTime' 使用严格大于，如果同一秒内有新记录可能遗漏
  • 双时间戳冗余：SYNC_TIME 和 INCREMENTAL_TIME 始终同步更新，功能重复

改进方案：

  1. 增量获取后，使用服务器返回的最新时间戳（而非客户端时间）作为下次增量基准
  2. 增量条件改为 >=，并在客户端去重（已处理的 ID 跳过）
  3. 合并 SYNC_TIME 和 INCREMENTAL_TIME 为统一的 LAST_SYNC_TIME
1.3.2 增量拼音生成优化 中优先 待开发

当前增量拼音生成逻辑：

  • 仅对新增/更新的 ID 生成拼音 ✅
  • 合并到已有拼音数据中 ✅
  • 未处理删除记录的拼音清理 ❌

改进：增量更新时，如果记录 deflag=1，需同步删除该记录的拼音数据。

依赖: 1.2.2
1.3.3 增量更新完整性校验 中优先 待开发

增量更新后增加数据完整性校验：

  • 校验本地记录总数与服务器返回的记录数是否一致
  • 校验拼音覆盖率（有拼音的记录数 / 总记录数）
  • 如果覆盖率低于阈值（如 95%），提示用户执行全量同步
  • 记录每次同步的日志（时间、类型、记录数、耗时）
依赖: 1.1.1 依赖: 1.3.1
板块二：匹配后操作接口

🚀板块二：匹配后操作接口

当前系统在匹配完成后，创建产品和创建订单都仅在前端本地操作，没有调用后端 API 将数据真正写入业务系统。需要补全这些接口，实现从"匹配"到"落库"的完整闭环。

🔴 现状问题：saveNewProduct() 只在 currentProducts 数组中标记 status='new'，generateOrder() 只弹出统计弹窗。两者都没有调用后端 API，数据不会写入业务系统。

2.1 创建产品接口

2.1.1 开发后端创建产品 API 高优先 待开发

新增创建产品接口，将前端新建的产品信息写入业务系统产品表：

// 请求参数
{
  cmd: 'create_data',
  dtname: 'product',
  data: {
    pro_name: '产品名称',     // 必填
    model: 'SKU编码',         // 可选
    spec: '规格型号',         // 可选
    unit: '个',              // 可选，默认'个'
    category: '其他',        // 可选
    remark: '备注'           // 可选
  }
}

// 返回
{
  code: 0,
  data: { id: 123, pro_name: '产品名称', ... }  // 返回新建记录的完整数据（含自动生成的id）
}
2.1.2 改造 saveNewProduct() 调用后端 API 高优先 待开发

改造 saveNewProduct() 函数（当前位于 index.html:1846-1876）：

  1. 收集表单数据，调用创建产品 API
  2. API 返回成功后，用返回的 id 更新 currentProducts 中的产品记录
  3. 自动为新创建的产品生成拼音索引，写入本地数据库
  4. 更新匹配状态为 confirmed，matchType 为 new
  5. API 失败时，保留前端标记但提示用户"产品创建失败，请稍后重试"
依赖: 2.1.1 依赖: 1.1.3

2.2.1 开发后端创建订单 API 高优先 待开发

2.2.2 改造 generateOrder() 调用后端 API 高优先 待开发

改造 generateOrder() 函数（当前位于 index.html:2209-2229）：

  1. 收集所有已确认的产品数据，组装订单请求参数
  2. 区分已匹配产品（status='confirmed'）和新建产品（status='new'）
  3. 新建产品需先调用创建产品 API，获取 product_id 后再组装订单
  4. 调用创建订单 API
  5. 成功：显示订单号，标记订单已提交
  6. 失败：提示错误信息，保留草稿数据供用户修改后重试
⚠️ 事务性：创建订单时如果包含新建产品，需确保"创建产品→获取ID→创建订单"的原子性。如果创建订单失败，已创建的产品不应回滚（产品已入库是合理的）。
