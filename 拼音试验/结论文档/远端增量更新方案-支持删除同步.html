远端增量更新方案

支持新增、修改、删除全场景的增量数据同步设计
创建：2026-05-19
对接：后端开发
涉及表：customer / product / 回收站 / 清空日志
1. 背景与问题

智能制单系统已实现基于时间戳的增量数据获取（详见《增量获取数据的算法》），通过客户表 amstamp 和产品表 modstm 字段筛选变更记录，实现了新增和修改数据的增量同步。

但当前方案存在一个关键缺陷：

无法感知删除：增量获取只能筛选出"有变更"的记录，无法获知哪些记录已被后台删除。前端 IndexedDB 中会残留已删除的脏数据，导致用户搜索到已失效的客户或产品。

此外，当前增量获取的合并策略是"新数据覆盖旧数据、旧数据保留"，这意味着：

操作类型当前能否同步说明
新增✅ 可以新记录的时间戳晚于基准时间，能被 where 条件筛选出来
修改✅ 可以修改后时间戳更新，能被筛选并覆盖旧数据
删除❌ 不可以删除后记录消失，无时间戳变化，前端无法感知
2. 方案总览

为解决删除同步问题，同时保持增量获取的小数据量优势，设计如下完整方案：

核心思路：将删除拆分为软删除（放入回收站）和硬删除（清空回收站）两个阶段，分别记录删除信息，每日增量同步时一并处理。
1
更新时间戳增量同步
客户表和产品表添加更新时间戳字段，通过 where 条件筛选出新增/修改的记录，
与前端 IndexedDB 按 id 合并——与现有逻辑一致，无需改动。
2
软删除记录同步
后台删除操作改为"放入回收站"（软删除），记录删除日期。
增量同步时查询回收站中当日新增的软删除记录，从前端 IndexedDB 中删除对应条目。
3
硬删除清空日志同步
回收站清空时，写入硬删除清空日志（记录被清空的记录 id 和类型）。
增量同步时查询清空日志，确保前端 IndexedDB 中对应条目被彻底删除。
4
每日增量小批量更新
结合上述三种数据源（变更记录 + 软删除 + 硬删除日志），
每日执行一次增量同步，实现与远端服务器的数据一致性。
3. 软删除与硬删除

将删除操作拆分为两个阶段，每个阶段都有可追溯的记录：

软删除（放入回收站）

  • 用户在主系统中删除客户/产品时，记录移入回收站
  • 记录标记为"已删除"状态，但数据仍保留在数据库中
  • 需要记录删除日期（deleted_at）
  • 回收站中的记录可恢复（还原操作）
  • 前端增量同步时，根据删除日期从 IndexedDB 中移除

硬删除（清空回收站）

  • 管理员清空回收站时，记录从数据库中物理删除
  • 数据不可恢复
  • 清空时写入硬删除清空日志
  • 日志记录被清空的记录 id、类型（客户/产品）、清空时间
  • 前端增量同步时，根据清空日志从 IndexedDB 中移除
为什么要区分两种删除？软删除是业务操作，有明确的删除时间和记录 id，可直接同步；硬删除是数据清理，记录已物理消失，必须依赖清空日志来追溯。如果只有硬删除而无日志，前端将无法获知哪些记录被彻底删除。
4. 数据库变更（后端需实现）

为实现上述方案，后端数据库需要以下变更：

A 客户表 / 产品表 — 添加更新时间戳

表现有字段新增字段说明
客户表 customerid, cu_name, amstamp无需新增amstamp 已满足需求
产品表 productid, pro_name, model, spec, modstm无需新增modstm 已满足需求
好消息：客户表和产品表已有更新时间戳字段（amstamp / modstm），新增/修改的增量同步无需额外改动。

B 回收站表 — 添加删除日期字段

字段类型说明
idINT回收站记录 id
source_idINT原始记录 id（客户 id 或产品 id）
source_typeVARCHAR来源类型：customer 或 product
source_nameVARCHAR原始记录名称（便于展示）
deleted_atDATETIME关键 删除日期时间
restored_atDATETIME还原日期时间（可为空）
关键要求：回收站表必须有 deleted_at 字段，且在记录放入回收站时自动写入当前时间。增量同步通过 where: deleted_at > '上次同步时间' 查询当日新增的软删除记录。

C 硬删除清空日志表 — 新增

字段类型说明
idINT日志 id（自增主键）
purge_timeDATETIME清空操作执行时间
source_typeVARCHAR来源类型：customer 或 product
source_idsTEXT / JSON被清空的原始记录 id 列表（JSON 数组格式）
operatorVARCHAR执行清空操作的用户
countINT被清空的记录数量
核心要求：回收站清空功能必须写入此日志表。source_ids 字段以 JSON 数组格式存储被清空的记录 id，例如 ["1","3","7"]。前端增量同步通过 where: purge_time > '上次同步时间' 查询新增的清空日志。
5. 接口设计（后端需实现）

在现有 load_data 接口基础上，新增两个查询：

接口1：查询软删除记录

// 查询回收站中当日新增的软删除记录
{
  "cmd": "load_data",
  "dtname": "recycle_bin",
  "field": "id,source_id,source_type,source_name,deleted_at",
  "where": "deleted_at > '2026-05-18 14:30:00' AND restored_at IS NULL",
  "flag": 1
}
返回字段说明：source_id 为原始客户/产品 id，source_type 区分客户或产品，restored_at IS NULL 排除已还原的记录。

接口2：查询硬删除清空日志

// 查询上次同步后的硬删除清空日志
{
  "cmd": "load_data",
  "dtname": "purge_log",
  "field": "id,purge_time,source_type,source_ids,count",
  "where": "purge_time > '2026-05-18 14:30:00'",
  "flag": 1
}
返回字段说明：source_ids 为 JSON 数组字符串，前端解析后得到被清空的 id 列表。source_type 区分客户或产品。
6. 每日增量同步流程
1
读取上次同步时间戳
从 IndexedDB 的 sync_status 表读取 incremental_time，
作为本次增量查询的基准时间。如不存在则提示先全量获取。
2
增量获取变更数据（新增/修改）
客户：where: amstamp > '基准时间'
产品：where: modstm > '基准时间'
按 id 合并到前端 IndexedDB，已有拼音字段保留。
3
查询软删除记录
回收站：where: deleted_at > '基准时间' AND restored_at IS NULL
根据 source_type 和 source_id，从前端 IndexedDB 的 customer / product 表中删除对应记录。
同时删除对应的拼音数据。
4
查询硬删除清空日志
清空日志：where: purge_time > '基准时间'
解析每条日志的 source_ids（JSON 数组），根据 source_type，
从前端 IndexedDB 中删除对应记录及拼音数据。
注：如果步骤3已删除，则步骤4是兜底确认，不会重复报错。
5
增量生成拼音
为步骤2中新增/修改的记录生成拼音，已有拼音保持不变。
6
5万上限截断检查
合并完成后，检查客户和产品的总条数是否超过 50,000。
超出时自动截断为前 50,000 条，弹出 toast 提示"总量超界，只取5万数据"，
保障 IndexedDB 中客户和产品的最大条数不超过各5万条。
7
更新同步时间戳
将当前时间写入 incremental_time，作为下次增量同步的基准。

9. 前端处理逻辑（伪代码） 
async function fetchIncrementalData() {
  var lastTime = await getSyncStatus('incremental_time');
  if (!lastTime) { showToast('请先全量获取'); return; }

  // 步骤1：增量获取变更数据（现有逻辑）
  var customerData = await sendLoadData({
    cmd: 'load_data', dtname: 'customer',
    field: 'id,cu_name,amstamp',
    where: "amstamp > '" + lastTime + "'", flag: 1
  });
  // ... 合并到 IndexedDB ...

  var productData = await sendLoadData({
    cmd: 'load_data', dtname: 'product',
    field: 'id,pro_name,model,spec,modstm',
    where: "modstm > '" + lastTime + "'", flag: 1
  });
  // ... 合并到 IndexedDB ...

  // 步骤2：查询软删除记录（新增）
  var recycleData = await sendLoadData({
    cmd: 'load_data', dtname: 'recycle_bin',
    field: 'id,source_id,source_type,deleted_at',
    where: "deleted_at > '" + lastTime + "' AND restored_at IS NULL",
    flag: 1
  });
  var recycleList = parseLoadDataResponse(recycleData);
  for (var i = 0; i < recycleList.length; i++) {
    var item = recycleList[i];
    if (item.source_type === 'customer') {
      await db.customer.delete(String(item.source_id));
    } else if (item.source_type === 'product') {
      await db.product.delete(String(item.source_id));
    }
  }

  // 步骤3：查询硬删除清空日志（新增）
  var purgeData = await sendLoadData({
    cmd: 'load_data', dtname: 'purge_log',
    field: 'id,purge_time,source_type,source_ids',
    where: "purge_time > '" + lastTime + "'",
    flag: 1
  });
  var purgeList = parseLoadDataResponse(purgeData);
  for (var j = 0; j < purgeList.length; j++) {
    var log = purgeList[j];
    var ids = JSON.parse(log.source_ids || '[]');
    for (var k = 0; k < ids.length; k++) {
      if (log.source_type === 'customer') {
        await db.customer.delete(String(ids[k]));
      } else if (log.source_type === 'product') {
        await db.product.delete(String(ids[k]));
      }
    }
  }

  // 步骤4：增量生成拼音
  await generateIncrementalPinyin(newCustomerIds, newProductIds);

  // 步骤5：5万上限截断检查
  var customers = await getCustomers();
  var products = await getProducts();
  if (customers.length > 50000) {
    customers = customers.slice(0, 50000);
    await setCustomers(customers);
    showToast('客户总量超界，只取5万数据', 'error');
  }
  if (products.length > 50000) {
    products = products.slice(0, 50000);
    await setProducts(products);
    showToast('产品总量超界，只取5万数据', 'error');
  }

  // 步骤6：更新时间戳
  var now = new Date().toISOString().replace('T', ' ').substring(0, 19);
  await setSyncStatus('incremental_time', now);
  await setSyncStatus('sync_time', now);
}
10. 实施任务清单

后端任务

  • 回收站表添加 deleted_at 字段 关键
    在现有回收站表中添加 deleted_at DATETIME 字段，删除操作时自动写入当前时间。同时添加 restored_at 字段记录还原时间。
  • 新增硬删除清空日志表 purge_log 关键
    创建 purge_log 表，包含 id、purge_time、source_type、source_ids、operator、count 字段。
  • 修改回收站清空逻辑 关键
    清空回收站时，先读取即将清空的记录 id 和类型，写入 purge_log 表，再执行物理删除。
  • 开放回收站和清空日志的 load_data 查询
    确保 load_data 接口支持 dtname: 'recycle_bin' 和 dtname: 'purge_log' 的查询，且 where 条件可正常过滤。

前端任务

  • 增量同步增加软删除查询步骤
    在 fetchIncrementalData 中新增对 recycle_bin 表的查询，根据返回的 source_id 和 source_type 从 IndexedDB 中删除对应记录。
  • 增量同步增加硬删除日志查询步骤
    在 fetchIncrementalData 中新增对 purge_log 表的查询，解析 source_ids JSON 数组，从 IndexedDB 中删除对应记录。
  • 更新同步进度提示
    增量同步进度条中增加"处理删除记录"步骤的提示，让用户了解同步进度。
11. 风险与注意事项
风险点影响应对措施
回收站清空时未写入日志 高 前端无法感知硬删除 后端必须在清空操作中强制写入 purge_log，作为事务的一部分
软删除后用户还原 中 前端已删除但记录实际未删除 还原操作会更新 amstamp/modstm，下次增量同步会重新获取该记录
source_ids JSON 过大 中 单次清空大量记录时日志过大 可按批次写入日志，每批最多 1000 个 id
增量同步期间新增删除 低 边界时间点的数据可能遗漏 下次增量同步会补上；定期全量获取可彻底消除差异
前端 IndexedDB 删除失败 低 脏数据残留 删除操作使用 Dexie 事务，失败会自动回滚；定期全量获取可清理
兜底方案：无论增量同步逻辑多么完善，建议保留"定期全量获取"作为兜底。例如每天首次使用时自动全量获取一次，或每周手动全量获取一次，确保数据最终一致。
