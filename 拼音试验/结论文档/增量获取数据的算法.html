增量获取数据算法

基于时间戳的增量数据同步与拼音自动生成机制
创建：2026-05-16
模块：get_cus_pro.html
接口：load_data
1. 背景与目标

智能制单系统需要从后台数据库获取客户和产品数据，并在前端生成拼音索引用于语音匹配。随着数据量增长，每次全量获取所有记录效率低下。

增量获取的目标：只请求上次同步后新增或修改的记录，减少网络传输和前端处理开销。

核心思路：利用数据库的更新时间字段（客户表 amstamp，产品表 modstm），在 load_data 接口的 where 条件中过滤出晚于上次同步时间的记录。
2. 数据表时间字段
数据表dtname更新时间字段字段含义
客户表customeramstamp客户信息最后更新时间
产品表productmodstm产品信息最后修改时间
前提条件：这两个字段必须由后台在记录创建和修改时自动维护。如果字段不存在或未正确更新，增量获取将无法正常工作。
3. localStorage 键值设计
LS Key类型说明
pinyin_tool_customersArray客户数据（id, name）
pinyin_tool_productsArray产品数据（id, name, model, spec）
pinyin_tool_customer_pinyinObject客户拼音索引（以id为key）
pinyin_tool_product_pinyinObject产品拼音索引（以id为key）
pinyin_tool_sync_timeString最后同步时间（显示用）
pinyin_tool_incremental_timeString新增 增量同步基准时间戳
时间戳格式：YYYY-MM-DD HH:mm:ss，与SQL标准兼容。例如 2026-05-16 14:30:00。
4. 全量获取流程
1
请求客户数据
请求参数：field: "id,cu_name,amstamp"，无 where 条件，获取全部客户记录。
返回数据标准化为 { id, name } 格式，直接覆盖写入 LS。
2
请求产品数据
请求参数：field: "id,pro_name,model,spec,modstm"，无 where 条件，获取全部产品记录。
返回数据标准化为 { id, name, model, spec } 格式，直接覆盖写入 LS。
3
记录时间戳
同时写入 pinyin_tool_sync_time 和 pinyin_tool_incremental_time，值为当前时间。
此时间戳作为后续增量获取的基准。 
// 全量获取请求参数
{
  "cmd": "load_data",
  "dtname": "customer",
  "field": "id,cu_name,amstamp",
  "flag": 1
}

// 完成后记录时间戳
var now = new Date().toISOString().replace('T', ' ').substring(0, 19);
localStorage.setItem(LS_KEY_SYNC_TIME, now);
localStorage.setItem(LS_KEY_INCREMENTAL_TIME, now);
5. 增量获取流程
0
前置检查
读取 pinyin_tool_incremental_time。如果不存在，说明从未进行过全量获取，
提示用户"请先全量获取"并终止。
1
增量请求客户数据
where 条件：amstamp > '上次时间戳'，只返回有变更的客户记录。
与 LS 中已有数据按 id 做 Map 合并（新数据覆盖旧数据），写回 LS。
2
增量请求产品数据
where 条件：modstm > '上次时间戳'，只返回有变更的产品记录。
同样按 id 合并到 LS。
3
自动增量生成拼音
调用 generateIncrementalPinyin(newCustomerIds, newProductIds)，
只为本次新增/变更的记录生成拼音，已有拼音数据保持不变。
4
更新时间戳
将当前时间写入 pinyin_tool_sync_time 和 pinyin_tool_incremental_time，
作为下次增量获取的基准。 
// 增量获取请求参数（客户）
{
  "cmd": "load_data",
  "dtname": "customer",
  "field": "id,cu_name,amstamp",
  "where": "amstamp > '2026-05-16 14:30:00'",
  "flag": 1
}

// 增量获取请求参数（产品）
{
  "cmd": "load_data",
  "dtname": "product",
  "field": "id,pro_name,model,spec,modstm",
  "where": "modstm > '2026-05-16 14:30:00'",
  "flag": 1
}
6. 数据合并策略

增量获取的数据需要与 LS 中已有数据合并，采用 按 id 覆盖 策略：

// 合并算法
var existing = getCustomers();          // LS中已有数据
var existingMap = {};
existing.forEach(function(c) { existingMap[c.id] = c; });  // 按id建Map
normalized.forEach(function(c) { existingMap[c.id] = c; }); // 新数据覆盖
var merged = Object.values(existingMap);  // 合并结果
setStore(LS_KEY_CUSTOMER, merged);
效果：相同 id 的记录被新数据覆盖（更新），不同 id 的记录保留（新增），LS 中有但接口未返回的记录也保留。
5万上限约束：增量合并后，如果客户或产品的总条数超过 50,000，将自动截断为前 50,000 条，弹出 toast 提示"总量超界，只取5万数据"，保障 IndexedDB 中客户和产品的最大条数不超过各5万条。 
// 增量合并后截断检查
if (merged.length > 50000) {
  merged = merged.slice(0, 50000);
  showToast('总量超界，只取5万数据', 'error');
}
7. 增量拼音生成

增量获取后自动调用 generateIncrementalPinyin(customerIds, productIds)，只处理变更的记录：

function generateIncrementalPinyin(customerIds, productIds) {
  var cp = getCustomerPinyin();   // 读取已有拼音（不重置）
  var pp = getProductPinyin();

  customerIds.forEach(function(id) {
    var c = customerMap[id];
    var py = generatePinyinForText(c.name);
    cp[id] = { id, name, pinyin, pinyin_abbr };  // 覆盖或新增
  });

  productIds.forEach(function(id) {
    var p = productMap[id];
    var combined = [p.name, p.model, p.spec].filter(...).join(' ');
    var py = generatePinyinForText(combined);
    pp[id] = { id, name, model, spec, pinyin, pinyin_abbr };
  });

  setStore(LS_KEY_PINYIN_CUSTOMER, cp);
  setStore(LS_KEY_PINYIN_PRODUCT, pp);
}
与全量拼音生成的区别：全量生成 generateAllPinyin 从 cp={} pp={} 开始重写所有拼音；增量生成从 getCustomerPinyin() 读取已有数据，只覆盖变更部分。
8. 全量 vs 增量对比
维度全量获取增量获取
where 条件无amstamp/modstm > 上次时间
返回数据量全部记录仅变更记录
LS 写入策略直接覆盖按 id Map 合并
拼音生成需手动触发全量生成自动增量生成
时间戳更新✅ 同步更新✅ 同步更新
清除已删除记录✅ 自然清除❌ 无法感知删除
适用场景首次使用 / 定期清理日常同步
9. 已删除记录的处理
已知限制：增量获取的 where 条件只能筛选出新增和修改的记录，无法感知后台已删除的记录。LS 中可能残留已删除的脏数据。

推荐做法：

方案做法适用场景
推荐 定期全量每天首次使用时点一次全量获取，其余时间用增量数据变更不频繁
可选 增量后校验增量获取后，再用 field:"id" 查一次全量 ID 列表，LS 中不在列表的删除对数据一致性要求高

    ▼

    ▼
