## 1. 权限测试

- [ ] **数据隔离基础**：不同账号登录后，同步下来的客户 / 产品数据须严格匹配自身权限
- [ ] **客户表权限**：仅具备**读权限**（无写、无删）
- [ ] **产品表权限**：仅具备**读权限**（无写、无删）
- [ ] **产品分组权限**：按"产品分组"裁剪后，只拉到本分组产品
- [ ] **产品全量权限**：拉到完整产品库
- [ ] **权限一致性切换**：同一账号切换"分组权限 ↔ 全量权限"后，本地 DEXIE 数据应跟随重拉

> 验证手段：分别用 2-3 个权限不同的账号登录，比对 IndexedDB 中 customer / product 表的 `id` 集合是否互不重叠且符合预期。

## 2. 增量同步测试

### 2.1 三种核心场景

#### ① 被删除的数据
- [ ] 软删除客户（CRM 端置删除标记）→ 本地增量后应被剔除
- [ ] 硬删除客户（CRM 端物理删除）→ 本地增量后应被剔除
- [ ] 软删除产品 → 本地增量后应被剔除
- [ ] 硬删除产品 → 本地增量后应被剔除

#### ② 被修改的数据
- [ ] 客户表（依托 `cu_amstamp` / `amstamp`）字段变更 → 增量同步应识别并拉取新数据
- [ ] 产品表（依托 `pr_modstm` / `modstm`）字段变更 → 增量同步应识别并拉取新数据
- [ ] 修改后 → 本地**拼音索引**（`pinyin` / `pinyin_abbr`）应自动重建

#### ③ 新增的数据
- [ ] 新增客户 → 增量同步应正确获取
- [ ] 新增产品 → 增量同步应正确获取
- [ ] 新增产品 → 拼音字段（`pinyin` + `pinyin_abbr`）应正确生成

### 2.2 自动同步逻辑

- [ ] **30 分钟节流**：自动同步 30 分钟内不重复触发（即便数据有变化）
- [ ] **智能判定同步方式**：自动同步会依据当前数据状态，**自动决定走「全量」还是「增量」**
  - 差异小 → 走增量
  - 差异大 → 走全量

### 2.3 兜底机制：差异 > 20% 触发全量

- [ ] **DEXIE 切换场景**：本地 DEXIE 数据（如 Demo Plus 版本）切换到正式库 `48004000` 时
- [ ] **20% 差异触发**：两个数据库整体差异 > **20%** → 系统**建议**执行全量同步
- [ ] **验证手段**（测试操作相对简单）：
  - [ ] 切换账号，制造"几乎全新"的本地数据 → 触发建议
  - [ ] 手工增 / 删大批量本地数据 → 触发建议
- [ ] **保护性兜底语义**：作为防"本地错乱数据污染新库"的最后一道防线

## 3. 测试优先级

| 优先级 | 模块 | 关键风险 |
|---|---|---|
| **P0** | 权限隔离 | 数据越权 → 合规问题 |
| **P0** | 删除场景（软+硬） | 本地残留已删数据 → 业务用错 → 工业生产事故 |
| **P1** | 修改 / 新增场景 | 拼音索引未更新 → 后续搜索不命中 |
| **P1** | 30 分钟节流 | 误判导致频繁全量 → 性能问题 |
| **P2** | 20% 差异兜底 | 边缘情况，保护机制验证 |

---

## 4. 建议测试顺序

1. **权限测试**（先确定数据范围，限定后续测试的"预期结果"）
2. **增量同步三种场景**（按 ② 修改 → ③ 新增 → ① 删除 顺序；删除最后测，避免误判为修改未生效）
3. **节流 + 智能判定**（在前述测试通过后，验证调度逻辑）
4. **20% 兜底机制**（最后单独验证，模拟极端数据差异）
