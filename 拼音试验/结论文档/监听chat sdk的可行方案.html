监听Chat SDK输出的可行方案

Coze WebChatClient 消息获取的踩坑记录与最终技术方案
创建：2026-05-16
实现：index2.html
SDK：Coze WebChatClient
API：Coze OpenAPI v1
1. 背景与需求

智能制单系统中，用户通过Coze智能体进行语音/文字对话，Coze解析后输出结构化JSON订单数据。原始方案（index.html）依赖剪贴板：用户手动复制Coze输出 → 监听剪贴板 → 解析JSON → 触发拼音匹配。

这个流程存在两个核心痛点：

痛点1：用户必须手动复制Coze输出，操作繁琐，容易遗漏
痛点2：剪贴板方案不支持语音输入场景——用户说话后Coze自动回复，但用户不会去手动复制

因此需要一种自动获取Coze对话结果的方案，实现"用户说话 → Coze回复 → 自动匹配"的闭环。

2. 方案评估与对比

方案A：SDK回调监听

  • 监听 onMessage 回调
  • Coze WebChatClient 不暴露消息回调
  • SDK是UI组件，非纯API库
  • 无语音输入能力

方案B：OpenAPI轮询

  • 定时调用Coze OpenAPI查询消息
  • 不依赖SDK内部实现
  • 支持语音输入场景
  • 与Chat SDK UI共存
结论：方案B（OpenAPI轮询）是唯一可行方案。Coze WebChatClient是封装好的UI组件，不提供消息级回调接口，无法从SDK内部获取对话内容。而OpenAPI轮询可以独立于SDK工作，同时保留SDK的语音输入和UI交互能力。
3. 踩坑记录（按时间顺序）
坑1：API路径错误
错误：使用了 /v3/conversation/list，返回404
原因：Coze API版本是v1，且路径命名不同
正确：/v1/conversations（会话列表），/v1/conversation/message/list（消息列表）
响应格式差异：res.data.conversations[0] 而非 res.data[0]
坑2：消息列表API方法错误
错误：使用GET请求 /v1/conversation/message/list，返回方法不允许
原因：Coze官方文档明确该接口是POST方法
修复：新增 cozeApiPost 函数，支持POST请求+JSON body
坑3：sort_order参数大小写
错误：传了 sort_order=DESC，API返回400
错误信息：请求参数 sort_order 不合法，该参数应当满足格式 should either be empty or in list ["asc", "desc"]
修复：改为小写 desc
坑4：connector_id缺失导致会话列表为空
现象：API返回 conversations: []，明明Chat SDK中有会话
原因：不传 connector_id 默认查询API渠道(1024)的会话，而Chat SDK创建的会话属于渠道999
修复：请求参数加上 connector_id=999
坑5：SDK参数命名风格
错误：将 bot_id 改为 botId（驼峰命名），导致Chat SDK对话框不显示
原因：旧版Coze WebChatClient SDK使用下划线命名（snake_case）
修复：改回 bot_id
坑6：JSON格式不匹配
现象：Coze输出 customer_name + products，但 extractJSONFromText 只识别 customer/客户/customerName
修复：增加 customer_name 格式支持，正则列表中添加 /\{[\s\S]*?"customer_name"[\s\S]*?"products"[\s\S]*?\}/
坑7：误标记已处理（最关键的Bug）
现象：第一次轮询提取到JSON后，handleClipboardText 静默失败，之后消息被标记为"已处理过"一直跳过
根因：handleClipboardText 内部调用 extractJSON 做二次解析，但 extractJSON 的正则匹配逻辑与 extractJSONFromText 不完全兼容，解析失败后 if (!data) return 静默退出，而外层轮询代码无条件标记 cozeLastMsgIds[msgKey] = true
修复：不再调用 handleClipboardText，轮询模块直接 JSON.parse → 构建orderDraft → 调用 showMatchProgress，且标记在 showMatchProgress 成功之后
坑8：CORS跨域问题
现象：浏览器直接调用 api.coze.cn 可能被CORS策略阻止
降级方案：封装 cozeApiGetWithProxy / cozeApiPostWithProxy，先尝试直接请求，CORS失败后降级处理
现状：当前SaaS服务器场景下CORS未触发，但保留降级逻辑作为防御
坑9：遍历所有消息导致重复处理旧内容
现象：如果最新消息没有JSON，轮询会继续遍历下一条旧消息，触发之前已处理过的订单
根因：代码逻辑是 for (var i = 0; i < answerMsgs.length; i++)，没有限制只处理最新一条
修复：简化逻辑，只处理 answerMsgs[0]（最新一条消息），不再遍历所有历史消息
坑10：页面加载时触发已有历史消息
现象：进入页面时，如果会话中已有历史订单消息，轮询会立即触发这些旧消息的匹配
根因：没有区分"页面加载前已存在的消息"和"页面加载后新出现的消息"
修复：新增 initialMessageIds 变量记录初始基准，在 startCozePolling 时先获取当前所有消息并记录ID，轮询时只处理基准之后的新消息
4. 最终技术方案

方案整体架构：Chat SDK负责UI交互和语音输入，OpenAPI轮询负责获取对话结果，两者通过会话ID关联。

1
初始化Chat SDK
加载Coze WebChatClient，配置bot_id和auth，渲染聊天UI组件。SDK初始化成功后启动轮询初始化。
0
【前置】记录初始消息基准
在正式开始轮询前，先调用API获取当前会话的所有消息，记录它们的ID到 initialMessageIds 作为基准。这些基准消息不会被处理。
2
定时轮询会话列表
每3秒调用 GET /v1/conversations?bot_id=xxx&connector_id=999&page_size=1&sort_order=desc，获取最新会话。
3
查询会话消息
调用 POST /v1/conversation/message/list?conversation_id=xxx，body为 {"order":"desc","limit":10}，获取最近10条消息。
4
过滤最新answer消息 + 双层去重
只取 answerMsgs[0]（最新一条），用 conv.id + "_" + latestAnswer.id 作为key，检查：①是否在 initialMessageIds（初始基准）②是否在 cozeLastMsgIds（已处理）。任一存在则跳过。
5
提取JSON
对最新这一条消息的content，用 extractJSONFromText 提取结构化JSON。支持 customer_name/customerName/customer/客户 等多种字段名格式，支持markdown代码块。
6
直接解析 + 构建orderDraft
JSON.parse 解析提取的JSON字符串，直接构建orderDraft对象（不经过handleClipboardText的二次解析），兼容多种字段命名风格。
7
触发匹配 + 标记已处理
调用 showMatchProgress(orderDraft) 触发拼音匹配和UI渲染。匹配成功后才标记 cozeLastMsgIds[msgKey]=true，失败时下次轮询会重试。

function fetchLatestConversation() {
  return cozeApiGetWithProxy(
    '/v1/conversations?bot_id=' + botId +
    '&connector_id=999&page_size=1&sort_order=desc'

    return res.data.conversations[0];

}

function fetchConversationMessages(conversationId) {

轮询初始化函数（新增）：

function startCozePolling() {
  if (cozePollTimer) clearInterval(cozePollTimer);
  var pollEl = document.getElementById('pollStatus');
  if (pollEl) pollEl.style.display = 'flex';
  updatePollUI('listening');

  // 初始化：先获取当前所有消息，记录它们的ID作为基准，不处理这些已有消息
  if (!isPollingInitialized) {
    updatePollUI('checking');
    fetchLatestConversation().then(function(conv) {
      if (conv) {
        fetchConversationMessages(conv.id).then(function(messages) {
          var answerMsgs = messages.filter(function(m) {
            return m.role === 'assistant' && m.type === 'answer';
          });
          answerMsgs.forEach(function(m) {
            initialMessageIds[conv.id + '_' + m.id] = true;
          });
          isPollingInitialized = true;
          updatePollUI('listening');
        });
      } else {
        isPollingInitialized = true;
        updatePollUI('listening');
      }
    });
  }

  cozePollTimer = setInterval(pollCozeMessages, 3000);
  setTimeout(pollCozeMessages, 1000);
}

轮询核心逻辑（修改后）：

function pollCozeMessages() {
  if (!getCozeToken() || !getCozeBotId()) return;
  // 未初始化时不处理消息
  if (!isPollingInitialized) {
    updatePollUI('listening');
    return;
  }

  updatePollUI('checking');

  fetchLatestConversation().then(function(conv) {
    if (!conv) { updatePollUI('listening'); return; }

    return fetchConversationMessages(conv.id).then(function(messages) {
      var answerMsgs = messages.filter(function(m) {
        return m.role === 'assistant' && m.type === 'answer';
      });

      if (answerMsgs.length > 0) {
        var latestAnswer = answerMsgs[0];  // 只处理最新一条消息
        var msgKey = conv.id + '_' + latestAnswer.id;

        // 双层去重检查：初始基准 OR 已处理
        if (initialMessageIds[msgKey] || cozeLastMsgIds[msgKey]) {
          updatePollUI('listening');
        } else {
          var jsonStr = extractJSONFromText(latestAnswer.content);

          if (jsonStr) {
            updatePollUI('found');

            try {
              var parsedObj = JSON.parse(jsonStr);

              var customerName = parsedObj.customer_name || parsedObj.customerName || parsedObj.customer || parsedObj['客户'] || '';
              var rawProducts = parsedObj.products || parsedObj.items || parsedObj['产品'] || [];

              var orderDraft = { source: 'coze_poll', ... };

              showMatchProgress(orderDraft);
              cozeLastMsgIds[msgKey] = true;
              lastDetectedJSON = jsonStr;
              updatePollUI('matched');
              showToast('Coze对话中检测到订单数据，已自动匹配', 'success');
            } catch (e) {
              updatePollUI('listening');
            }
          } else {
            updatePollUI('listening');
          }
        }
      } else {
        updatePollUI('listening');
      }

      pollRetryCount = 0;
    });
  }).catch(function(e) {
    pollRetryCount++;
    // ... 错误处理
  });
}
6. 关键设计决策
决策点 选择 原因
消息获取方式 OpenAPI轮询 SDK不暴露消息回调，轮询是唯一可行方案
轮询间隔 3秒 平衡实时性与API调用频率，Coze回复通常需5-10秒
connector_id 999 Chat SDK创建的会话属于渠道999，不传则查不到
消息去重策略 双层去重：initialMessageIds + cozeLastMsgIds initialMessageIds过滤初始基准消息，cozeLastMsgIds过滤已处理过的消息
消息处理范围 只处理最新一条 避免触发旧消息，保证只对用户当前对话的最新回复做反应
JSON解析路径 直接JSON.parse 绕过handleClipboardText的extractJSON二次解析，避免格式不兼容
标记时机 showMatchProgress之后 匹配失败时不标记，下次轮询可重试
字段兼容 多格式映射 Coze输出格式可能变化，需兼容customer_name/customerName/customer等
CORS处理 降级策略 直接请求失败时降级，当前SaaS场景未触发但保留防御
重置逻辑 重置initialMessageIds + 重新初始化 点击"重新录入"后重置所有状态，重新记录初始基准，避免触发旧内容

8. 踩坑总结与经验
经验1：SDK ≠ API
Coze WebChatClient是UI组件，不是API库。它封装了完整的聊天界面，但不暴露内部消息流。需要获取对话内容时，必须走独立的OpenAPI通道，不能指望SDK回调。
经验2：渠道隔离
Coze的会话按渠道（connector）隔离。Chat SDK（渠道999）和OpenAPI（渠道1024）创建的会话互不可见。查询Chat SDK的会话时必须指定 connector_id=999，否则返回空列表。
经验3：避免二次解析
两个独立的JSON提取函数（extractJSONFromText和extractJSON）格式兼容性有微妙差异。当A函数提取的结果交给B函数二次解析时，可能因格式不兼容而静默失败。最终方案是单一解析路径：extractJSONFromText提取 → JSON.parse直接解析 → 构建业务对象。
经验4：标记时机决定重试能力
"已处理"标记必须在业务逻辑成功执行之后才设置。如果先标记再执行，一旦执行失败，该消息永远不会被重试。这是"误标记已处理"Bug的根因。
经验5：API参数大小写敏感
Coze OpenAPI对参数值的大小写严格校验。sort_order=DESC 会被拒绝，必须是 desc。这种细节在官方文档中容易忽略，只能通过实际调试发现。
经验6：SDK参数命名风格
不同版本的SDK可能使用不同的命名风格（snake_case vs camelCase）。Coze旧版WebChatClient SDK使用 bot_id，改为 botId 会导致SDK初始化失败但不报错。修改SDK参数前务必确认版本对应的命名规范。
经验7：区分"初始已有"与"后续新增"消息
页面加载时会话中可能已存在历史消息，这些消息不应被触发。必须在正式轮询前先记录一个"初始基准"（initialMessageIds），后续只处理基准之后的新消息。
经验8：限制消息处理范围
不要遍历所有历史消息，只处理最新一条（answerMsgs[0]）。否则如果最新消息没有JSON，可能会继续处理旧消息导致重复触发。
