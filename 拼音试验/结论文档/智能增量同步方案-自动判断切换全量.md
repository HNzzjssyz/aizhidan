# 智能增量同步方案

> 整合"增量同步 + 全量同步"为单一入口，后台自动判断使用哪种同步方式
> 支持**新增 / 修改 / 删除**三类数据的本地库与远端库保持一致
> 适用版本：v1.0（2026-06-05 讨论结论落地）

**v1.4 升级**（2026-06-10）：
- **产品表拉取字段新增 `price`（价格/单价）**：
  - 增量同步：`field: 'id,pro_name,model,spec,price,modstm'`
  - 全量同步：`field: 'id,pro_name,model,spec,price'`
  - 同步组装时 `price: item.price || ''`，前端 `selectProductForEdit` / `fillProductStandardData` / 三个 `fuzzyMatch*` 函数透传 `matchedPrice` / `price` 到候选对象
  - 选择产品弹窗在每条候选下方显示「参考价：¥xx.xx」（无值时显示灰色"待询价"）
- **拼音生成跳过判断纳入 price 字段**：产品拼音 `pp[key]` 写回时带 `price: p.price || ''`；跳过判断在原 `name/model/spec` 基础上增加 `existing.price === (p.price || '')`，价格变化会触发重新生成拼音
- **修复 `DatabaseClosedError: Database has been closed`**（Safari 长时间挂起后 IDB 被自动关闭）：
  - `initDB()` 增加 `db.isOpen()` 检测 + 警告日志
  - 13 个 db 访问点（读 / 写 / 事务）入口前显式 `if (!db.isOpen()) await db.open()`，自动重连

**v1.3 修正**（2026-06-08）：
- 重要更正：服务器 `load_data` 接口<strong>并不会自动追加</strong> `dflag` / `status` 全局过滤条件，所有过滤都<strong>必须由客户端在 where 中显式写入</strong>。
- **客户表（customer）**：`where` 加 `dflag=0` 排除回收站（业务上"放入回收站"= 软删除；物理删除走差异检测的 `extraOnLocal`）。
- **产品表（product）**：`where` 加 `dflag=0 AND status=0`，同时排除回收站数据（`dflag=1`）和停售产品（`status=1`）。
- 拉取字段保持不变：客户 = `id,cu_name,amstamp`；产品 = `id,pro_name,model,spec,modstm`（仍不拉 dflag / status）— **v1.4 起产品字段已新增 `price`**

**v1.2 修正**（2026-06-05）：
- **客户表（customer）允许物理删除**（无日志），删除检测**必须用二分法**（恢复 v1.0 §3.2.3 原始方案）
- **产品表（product）采用 dflag 软删除 + status 停售**，由<strong>客户端在 where 中显式加</strong> `dflag=0 AND status=0`（v1.3 修正；服务器不自动追加 dflag / status 过滤）
- 拉取字段：客户 = `id,cu_name,amstamp`；产品 = `id,pro_name,model,spec,modstm`
- 详见 [dflag 的全局条件.md](../读取数据接口/dflag的全局条件.md)

## 1. 背景与目标

### 1.1 现状问题

- **客户表允许物理删除**（无删除日志），现有增量逻辑无法感知"远端已删的本地僵尸数据"
- **客户表也支持"放入回收站"（软删除，dflag=1）**：v1.3 之前客户端未在 where 中加 dflag=0 过滤，会把回收站数据也同步到本地 → 已修复
- **产品表采用 dflag 软删除 + status 停售**：v1.3 之前客户端只在 where 中加 `modstm > lastTime`，不过滤 dflag / status，会把停售品和已删品同步到本地 pinyin 库 → 已修复，现在统一在 where 中加 `dflag=0 AND status=0`
- **当前只有"增量"和"全量"两个按钮**：用户需手动判断使用哪种，认知负担重
- **现有阈值 5000 触发切全量**：但仅基于"新增量"判断，**没考虑差异率**

### 1.2 方案目标

1. **统一入口**：合并为单个"同步数据"按钮，**后台自动判断**使用增量还是全量
2. **完整性**：覆盖新增 / 修改 / 删除**三类数据**
3. **智能化**：基于"差异率"而非"绝对量"判断切全量（更合理）
4. **健壮性**：网络抖动、计数失败时**降级为全量分片**

### 1.3 涉及数据表

| 表名 | 增量标识字段 | 业务主键 |
|------|------------|---------|
| `customer` 客户 | `amstamp`（最后修改时间） | `id` |
| `product` 产品 | `modstm`（最后修改时间） | `id` |

### 2.2 三种数据处理策略对照

| 表 | 数据类型 | 检测方法 | 处理动作 |
|----|---------|---------|---------|
| **客户 customer**（物理删除 / 回收站软删除）| 新增 | 本地最大ID < 服务器最大ID | 按 ID 范围拉取缺失 ID 的完整数据 |
| | 修改 | `amstamp` > 上次同步时间 | 按时间戳增量拉取（客户端 where 加 `dflag=0` 排除回收站）|
| | 删除 | 远端未返回的本地 ID | 物理删除：差异检测 extraOnLocal；软删除：`dflag=1` 走客户端 dflag=0 过滤 |
| **产品 product**（dflag 软删除 + status 停售）| 新增 | 本地最大ID < 服务器最大ID | 按 ID 范围拉取缺失 ID 的完整数据 |
| | 修改 | `modstm` > 上次同步时间 | 按时间戳增量拉取（客户端 where 加 `dflag=0 AND status=0`）|
| | 删除 / 停售 | 远端未返回的本地 ID | 从本地 `product` 表删除（`dflag=1` 软删 / `status=1` 停售触发）|

## 3. 核心算法

### 3.1 差异检测（决定切全量还是增量）

**目标**：用最少请求判断"本地 vs 远端"差异程度

**算法**：**ID 采样对比法**

```javascript
// 1. 拉取远端所有 ID（轻量字段，只取 id）
//    用分页避免一次拉太多
var serverIds = await fetchServerIds({ page: 1, pageSize: 5000 });
//    翻页直到拿完

// 2. 本地 ID 集合
var localIds = new Set((await getCustomers()).map(c => c.id));

// 3. 计算差异
var missingOnLocal = serverIds.filter(id => !localIds.has(id));  // 远端有本地无 → 新增
var extraOnLocal  = [...localIds].filter(id => !serverIds.includes(id));  // 本地有远端无 → 删除

// 4. 差异率
var diffRate = (missingOnLocal.length + extraOnLocal.length) / serverIds.length;

// 5. 决策
if (diffRate > 0.2) {
  // 差异超过 20% → 切全量
  await fetchFullData();
} else {
  // 进入增量流程
  await incrementalSync({ missingOnLocal, extraOnLocal });
}
```

**为什么是 20%**：
- 5% 容易触发全量（缺乏增量意义）
- 50% 容忍度过高（增量收益小）
- **20% 经验值** — 差异小时增量快且准，差异大时全量更省心

**边界保护**：

```javascript
// 远端总数 < 1000 时强制走全量（增量分页开销不划算）
if (serverIds.length < 1000) {
  await fetchFullData();
  return;
}

// 拉取远端 ID 失败时降级为全量（保守策略）
try {
  serverIds = await fetchServerIds();
} catch (e) {
  log('差异检测失败，降级为全量', 'err');
  await fetchFullData();
  return;
}
```

### 3.2 增量同步算法（差异率 ≤ 20% 时走此路径）

**三步走**：

#### 3.2.1 新增数据：ID 对比法

```javascript
// 上次同步后，本地最大 ID
var localMaxId = Math.max(...localIds);

// 服务器拉取 ID > localMaxId 的记录
var newIds = serverIds.filter(id => id > localMaxId);

// 拉取这些新 ID 的完整数据
var newRecords = await fetchByIds(newIds);
```

**适用条件**：服务器 ID 单调递增（ID 大的必然是新加的）
**优势**：1 次请求就能拿到所有新增 ID，再批量拉数据

#### 3.2.2 修改数据：时间戳对比法

```javascript
// 上次同步时间
var lastTime = await getSyncStatus('incremental_time');

// 拉取 amstamp > lastTime 的客户（修改过的）
// v1.3 起：where 显式加 dflag=0 排除回收站
var modifiedCustomers = await loadData({
  dtname: 'customer',
  field: 'id,cu_name,amstamp',
  where: `amstamp > '${lastTime}' AND dflag=0`
});

// 同样拉取产品
// v1.3 起：where 显式加 dflag=0 AND status=0 排除回收站 + 停售
var modifiedProducts = await loadData({
  dtname: 'product',
  field: 'id,pro_name,model,spec,modstm',
  where: `modstm > '${lastTime}' AND dflag=0 AND status=0`
});
```

**注意**：时间戳精度问题（已确认两字段都是时间戳类型，方案兼容秒级/毫秒级两种精度）
- 数据库 `amstamp` / `modstm` 是 `DATETIME(3)`（毫秒精度）或 `DATETIME`（秒级）
- JS 端 `new Date().toISOString()` 默认是 `DATETIME(6)`（微秒精度）
- **推荐**用 `substring(0, 19)` 截取秒级时间戳（兼容两种精度），**不会漏拉边界数据**
  - 毫秒级字段：'2026-06-05 14:23:45' 被解释为 '...45.000'，下一条 '...45.123' 仍 > 此值
  - 秒级字段：'2026-06-05 14:23:45' 是标准格式

#### 3.2.3 删除数据：客户表（物理删除）— 二分法

**业务事实**（v1.2 修正）：
- 客户表（`customer`）**允许物理删除**（硬删除）
- **无删除日志**，本地无法通过日志感知
- 必须通过**远端 ID 列表 vs 本地 ID 集合**的对比来识别"被删的客户"

**算法**：**二分法**——在远端 ID 列表（已排序）中快速定位"缺失段"

```javascript
// serverIds 远端 ID 列表（升序）
// localIds  本地 ID 集合

function findMissingIds(serverIds, localIds, lo = 0, hi = serverIds.length - 1) {
  var missing = [];

  // 递归终止
  if (lo > hi || hi - lo < 10) {
    // 区间足够小，逐个对比
    for (var i = lo; i <= hi; i++) {
      if (!localIds.has(serverIds[i])) missing.push(serverIds[i]);
    }
    return missing;
  }

  var mid = Math.floor((lo + hi) / 2);
  var midId = serverIds[mid];

  if (localIds.has(midId)) {
    // midId 存在，左半段（lo..mid-1）大概率都存在
    // 重点查右半段（mid+1..hi）
    missing = missing.concat(findMissingIds(serverIds, localIds, mid + 1, hi));
    // 左半段中 lo..mid-1 也需抽样核查
    if (lo < mid) {
      missing = missing.concat(findMissingIds(serverIds, localIds, lo, mid - 1));
    }
  } else {
    // midId 不存在，整段都可能有问题
    missing.push(midId);
    missing = missing.concat(findMissingIds(serverIds, localIds, lo, mid - 1));
    missing = missing.concat(findMissingIds(serverIds, localIds, mid + 1, hi));
  }

  return missing;
}
```

**复杂度**：
- 直接遍历：O(n)
- 二分法：O(n × log(n) × 段内开销) — **适用于差异率小的场景**

**适用条件**：
- 远端 ID 列表**有序**（数据库默认主键索引有序）
- 缺失率 < 20%（否则效率退化，全量更划算）

**与差异检测的协作**：
- §3.1 步的"差异检测"已经计算了 `extraOnLocal`（本地有远端无 = 被删的）
- **3.2.3 不需要重新跑二分**，直接消费 §3.1 的结果
- `findMissingIds()` 作为独立函数保留，仅用于调试 / 离线场景

#### 3.2.4 删除数据：产品表（软删除 + 停售）— 客户端 where 显式过滤

**业务事实**（v1.3 修正）：
- 产品表（`product`）**不允许物理删除**，采用 `dflag` 软删除
- `dflag=1` 表示已删除（回收站），`dflag=0` 表示正常
- `status=1` 表示停售，`status=0` 表示在售
- **v1.3 重要更正**：服务器 `load_data` 接口<strong>不会自动追加</strong> `dflag` / `status` 过滤条件
- 客户端必须在 where 中显式加 `dflag=0 AND status=0`，同时排除回收站和停售

**为什么必须由客户端过滤**（v1.3 修正）：

旧方案 v1.2 假设服务器通过 `api-client.js` / `multi-table-query.js` 的 `GLOBAL_WHERE_CONDITIONS` 自动追加 `dflag != 1`。**实际验证后这个假设是错的**：
- 实际服务器对 `load_data` 接口没有全局过滤机制
- `dflag` 字段的"软删除语义"只对业务查询接口（如 `get_data`、`list_data`）有效
- 客户端如果不在 where 中显式过滤，会把 `dflag=1` 的回收站数据和 `status=1` 的停售产品同步到本地 pinyin 库，导致：
  1. **做单员看到已删除/已停售的产品** → 选错品下单
  2. **diffRate 计算失真** → 回收站 ID 算作"本地缺失"，抬高差异率，可能误触发全量同步
  3. **本地数据污染** → 需要单独写清理脚本

**算法**：

```javascript
// 1. 拉取产品数据
//    - field 仍不含 dflag / status（拉了也只会被客户端过滤）
//    - where 必须显式含 dflag=0 AND status=0（v1.3 强制）
var productParams = {
  cmd: 'load_data',
  dtname: 'product',
  field: 'id,pro_name,model,spec,price,modstm',             // v1.4 起加 price；不含 dflag / status
  where: `modstm > '${lastTime}' AND dflag=0 AND status=0`, // 客户端显式过滤
  flag: 1
};
// 客户端拼出最终 SQL：SELECT id,pro_name,model,spec,price,modstm FROM product
//                      WHERE modstm > '...' AND dflag=0 AND status=0

// 2. 合并时基于"远端最新状态"处理
//    - 远端返回的记录 → 视为有效（dflag=0 且 status=0）→ 更新到本地
//    - 远端未返回但本地存在的记录 → 三种可能：
//      a) dflag=1（放入回收站）
//      b) status=1（停售）
//      c) 物理删除（理论上产品表不允许，但兜底）
//      → 全部归入 extraOnLocalProducts，从本地删除
modifiedProducts.forEach(function(p) {
  productMap[p.id] = p;
});
// 远端未返回的产品由差异检测阶段的 extraOnLocalProducts 清理
```

**关键变更（v1.3 vs v1.2）**：

| 维度 | v1.2（旧假设）| v1.3（实际） |
|------|-------------|-------------|
| 服务器是否自动追加 dfilter | 是（api-client.js GLOBAL_WHERE_CONDITIONS） | **否** |
| 客户端 where 是否含 dflag | 否 | **是（dflag=0）** |
| 客户端 where 是否含 status | 否 | **是（status=0）** |
| 拉取字段是否含 dflag / status | 否 | 否 |
| 本地清理依据 | §3.1 extraOnLocalProducts | §3.1 extraOnLocalProducts（同一来源） |
| 过滤涵盖范围 | 仅 dflag=1 | dflag=1 + status=1 |

**与客户表删除的差异**：

| 维度 | 客户表（物理删除 / 回收站软删除） | 产品表（软删除 + 停售） |
|------|-------------------|------------------|
| 远端删除方式 | 物理 DELETE / 软删除（dflag=1）| 软删除（dflag=1）|
| 远端停售方式 | —（无此状态）| UPDATE product SET status=1 |
| 远端是否会返回 | 已删不返回 | 已删 / 已停售不返回（客户端 where 过滤）|
| 拉取字段是否含 dflag / status | 否 | 否 |
| where 是否显式含 dflag / status | **是（dflag=0）** | **是（dflag=0 AND status=0）** |
| 本地清理依据 | §3.1 差异检测 extraOnLocal | §3.1 差异检测 extraOnLocalProducts（同一来源） |
| 是否需要二分法 | 是 | 否 |

### 3.3 本地合并

```javascript
// ========== 1. 客户合并（物理删除 + 回收站软删除）==========
// extraOnLocal = §3.1 差异检测阶段计算出的"本地有但远端无"的 ID
// missingOnLocal = §3.1 计算出的"远端有但本地无"的 ID
// v1.3 起：where 显式加 dflag=0，已过滤回收站；extraOnLocal = 物理删除的客户
var existingCustomers = await getCustomers();
var customerMap = {};
existingCustomers.forEach(c => { customerMap[c.id] = c; });

// 新增（本地缺的）+ 修改（远端返回的 amstamp 变化）
modifiedCustomers.forEach(c => { customerMap[c.id] = c; });

// 删除：远端物理删除的客户 = 远端未返回的本地记录
extraOnLocal.forEach(id => { delete customerMap[id]; });

// 截断保护
var mergedCustomers = Object.values(customerMap);
if (mergedCustomers.length > CUSTOMER_LIMIT) {
  mergedCustomers = mergedCustomers.slice(0, CUSTOMER_LIMIT);
}
await setCustomers(mergedCustomers);

// ========== 2. 产品合并（软删除 + 停售）==========
// v1.3 起：where 显式加 dflag=0 AND status=0，已过滤回收站和停售
// 远端未返回的本地产品 = 软删除（dflag=1）或停售（status=1）
var existingProducts = await getProducts();
var productMap = {};
existingProducts.forEach(p => { productMap[p.id] = p; });

// 新增 + 修改
modifiedProducts.forEach(p => { productMap[p.id] = p; });

// 删除 / 停售：远端未返回的本地记录
extraOnLocalProducts.forEach(id => { delete productMap[id]; });

// 截断保护
var mergedProducts = Object.values(productMap);
if (mergedProducts.length > PRODUCT_LIMIT) {
  mergedProducts = mergedProducts.slice(0, PRODUCT_LIMIT);
}
await setProducts(mergedProducts);
```

**关键差异**：
- 客户：必须**显式**根据 `extraOnLocal` 删除（服务器已物理删除，无其他线索）
- 产品：根据 `extraOnLocalProducts` 删除（服务器已通过客户端 where 过滤掉 dflag=1 / status=1，逻辑相同）

### 3.4 拼音生成（仅对变化项）

```javascript
async function generatePinyinForChanges(newIds, modifiedIds, deletedIds) {
  // 1. 加载已有拼音
  var cp = await getCustomerPinyin();
  var pp = await getProductPinyin();
  var customers = await getCustomers();
  var products = await getProducts();
  
  // 2. 客户拼音：仅处理新增/修改，名字未变则跳过
  var changedIds = [...new Set([...newIds, ...modifiedIds])];
  customers.filter(c => changedIds.includes(c.id)).forEach(c => {
    if (cp[c.id] && cp[c.id].name === c.name) return;  // 名字未变，跳过
    var py = generatePinyinForText(c.name);
    cp[c.id] = { id: c.id, name: c.name, pinyin: py.full, pinyin_abbr: py.abbr };
  });
  
  // 3. 客户拼音：删除已被合并步骤清理的 ID
  deletedIds.forEach(id => { delete cp[id]; });
  
  // 4. 产品拼音：同样逻辑（处理 name/model/spec 三个字段的合并）
  // ...
  
  // 5. 写入数据库
  await setCustomerPinyin(cp);
  await setProductPinyin(pp);
}
```

**优化点**：
- 用 `cp[c.id].name === c.name` 跳过名字未变的客户
- 减少 pinyinPro 调用次数（pinyinPro 单次调用约 1-3ms）

async function syncData() {
  var lastTime = await getSyncStatus('incremental_time');
  var isFirstTime = !lastTime;
  
  // 首次同步强制全量
  if (isFirstTime) {
    log('首次同步，执行全量获取', 'info');

  }
}

## 5. 异常处理与降级

### 5.1 异常场景处理表

| 异常场景 | 检测点 | 处理策略 |
|---------|--------|---------|
| 远端 ID 拉取失败 | `fetchServerIds()` 抛错 | 直接走全量分片 |
| 时间戳查询失败 | `loadData` 抛错 | 走全量分片 |
| 二分定位超时 | 递归深度 > 阈值 | 切换为全量分片 |
| 单条数据写入失败 | IndexedDB `put` 抛错 | 跳过该条，继续后续 |
| 拼音生成失败 | pinyinPro 抛错 | 保留旧拼音，标记待重试 |
| 远端返回 401/403 | HTTP 状态码异常 | 停止同步，提示用户重新登录 |

### 5.2 降级逻辑核心

```javascript
async function safeSync(strategy) {
  try {
    if (strategy === 'full') {
      await fetchFullData();
    } else {
      await incrementalSync();
    }
  } catch (e) {
    if (e.isRecoverable) {
      // 可恢复异常：网络/服务器临时故障 → 切全量重试
      log('增量失败，降级为全量：' + e.message, 'err');
      await fetchFullData();
    } else {
      // 不可恢复异常：权限/数据错误 → 中止并提示
      log('同步中止：' + e.message, 'err');
      throw e;
    }
  }
}
```

## 6. 数据一致性保障

### 6.1 幂等性

- **多次执行结果一致**：基于 ID 集合的运算天生幂等
- **中断后重试安全**：本地有变化则远端补全，远端有新增则本地插入

### 6.2 事务性

- 每条记录独立处理，**单条失败不影响其他**
- 最后写 `incremental_time` 之前先做完整性检查（数量匹配）

### 6.3 并发安全

- 同一时刻**只允许一个同步任务**（UI 层禁用按钮）
- 同步中**不响应外部触发**（避免数据错乱）

```javascript
var _syncing = false;

async function syncData() {
  if (_syncing) {
    showToast('同步进行中，请勿重复点击', 'warning');
    return;
  }
  _syncing = true;
  try {
    // ... 同步逻辑
  } finally {
    _syncing = false;
  }
}
```

## 7. 性能预算

| 步骤 | 1万级客户 | 10万级客户 |
|------|----------|----------|
| 拉取远端 ID 列表 | 1-2 秒 | 5-10 秒（分页） |
| 计算差异率 | < 100ms | < 1 秒 |
| 拉取新增数据 | 1-2 秒 | 5-10 秒 |
| 拉取修改数据 | 1-2 秒 | 5-10 秒 |
| 本地合并 | < 500ms | < 3 秒 |
| 拼音生成（仅变化项）| 1-3 秒 | 5-15 秒 |
| **总计（增量场景）** | **5-10 秒** | **25-45 秒** |
| **总计（全量场景）** | **20-40 秒** | **3-5 分钟** |

**结论**：
- 1万级数据下，增量比全量快 **3-5 倍**
- 10万级数据下，增量比全量快 **5-10 倍**
- 差异率 ≤ 20% 时增量收益显著，> 20% 时全量更省心
