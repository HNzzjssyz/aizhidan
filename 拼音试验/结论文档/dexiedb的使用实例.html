为什么选择 Dexie.js

本系统（AI智能制单）需要将客户和产品数据存储在浏览器端，以支持离线拼音匹配。原方案使用 localStorage，存在以下瓶颈：

对比维度localStorageDexie (IndexedDB)
存储容量~5MB / 源数百MB甚至GB
数据类型仅字符串（需 JSON 序列化）结构化数据，直接存对象
查询能力全量读取 + JS 过滤索引查询、范围查询、游标
写入性能同步阻塞，大数据量卡顿异步非阻塞，bulkPut 批量写入
事务支持无完整事务（readwrite / readonly）
选型结论：Dexie.js 是 IndexedDB 的轻量封装库（~30KB），提供链式 API、Promise 支持、事务管理，完美满足本系统"5万客户+5万产品+拼音索引"的存储与查询需求。

关键设计：所有 Dexie 操作封装在 PinyinMatch 闭包内，UI 层不直接操作 Dexie，只通过闭包暴露的 API 访问数据。缓存层对 UI 透明——调用方无需关心数据来自内存还是 IndexedDB。
数据库定义与初始化

数据库定义在 pinyin_match.js 的 initDB() 函数中：

var db = null;

function initDB() {
  if (db) return db;  // 单例模式，避免重复创建
  db = new Dexie('PinyinToolDB');
  db.version(1).stores({
    customer:    'id, name, pinyin, pinyin_abbr, update_time',
    product:     'id, name, model, sku, pinyin, pinyin_abbr, update_time',
    sync_status: 'key'
  });
  return db;
}
表名主键索引字段用途
customer id name, pinyin, pinyin_abbr, update_time 客户基础数据 + 拼音索引
product id name, model, sku, pinyin, pinyin_abbr, update_time 产品基础数据 + 拼音索引
sync_status key （无额外索引） 键值对存储同步时间戳等元数据
stores() 中只声明索引字段，不是全部字段。Dexie 允许存储任意结构的对象，stores() 中列出的字段仅用于建立索引。例如 customer 表实际存储的字段包括 address、contact、code 等，但它们不需要索引，所以不在 stores() 中声明。

初始化入口——两个函数的区别：

函数返回值使用场景
initDB() Dexie 实例（同步） 内部各函数开头调用，确保 db 已初始化
init() Promise<Dexie> UI 层入口：PinyinMatch.init().then(...) 
// index.html 中的初始化

基础读写 API
getCustomersAsync() 读取
读取客户表全量数据。内部调用 db.customer.toArray()，返回对象数组。
var customers = await PinyinMatch.getCustomersAsync(); // [{id, name, pinyin, ...}, ...]
getProductsAsync() 读取
读取产品表全量数据。内部调用 db.product.toArray()。
var products = await PinyinMatch.getProductsAsync(); // [{id, name, model, sku, pinyin, ...}, ...]
getCustomerPinyinAsync() / getProductPinyinAsync() 读取
读取拼音索引数据，返回 {id: {pinyin, pinyin_abbr}} 格式的映射表。内部先 toArray() 全量读取，再 forEach 提取拼音字段。
var pinyinMap = await PinyinMatch.getProductPinyinAsync(); // {"123": {pinyin: "chan pin", pinyin_abbr: "cp"}, ...}
setCustomersAsync(customers) 写入
全量替换客户数据。先将所有 id 转为字符串，再 clear() + bulkPut() 清空后批量写入。写入后自动调用 invalidateCustomerCache() 清除缓存。
await PinyinMatch.setCustomersAsync(customerArray);
setProductsAsync(products) 写入
全量替换产品数据。逻辑同 setCustomersAsync，写入后自动调用 invalidateProductCache()。
await PinyinMatch.setProductsAsync(productArray);
id 字段统一转字符串：setCustomersAsync 和 setProductsAsync 内部都会执行 obj.id = String(obj.id)，确保主键类型一致。这是因为后端返回的 id 可能是数字，而 Dexie 主键类型必须统一。
内存缓存层

IndexedDB 读取是异步 I/O 操作，每次 toArray() 全量读取5万条数据需要数十毫秒。在制单匹配流程中，同一批数据可能被多次访问（产品匹配、客户匹配、填充表单等），重复读取会造成性能浪费。因此设计了内存缓存层。

缓存变量类型来源用途
_productsCache Array db.product.toArray() 产品全量数据
_customersCache Array db.customer.toArray() 客户全量数据
_productMapCache Object 由 _productsCache 派生 id → 产品对象，O(1) 查找
_customerMapCache Object 由 _customersCache 派生 id → 客户对象，O(1) 查找
_nameIndexCache Object 由 _productsCache 派生 产品名小写 → 产品数组，精确匹配
_indexDbCache Array 由 _productsCache 派生 产品拼音索引条目
_customerIndexDbCache Array 由 _customersCache 派生 客户拼音索引条目
_tokenInvertedIndex Object 由 _indexDbCache 派生 拼音 token → 产品索引集合，倒排索引
_customerTokenInvertedIndex Object 由 _customerIndexDbCache 派生 拼音 token → 客户索引集合，倒排索引

缓存读取模式——以 getProductsCached() 为例：

async function getProductsCached() {
  if (_productsCache) return _productsCache;  // 命中缓存，直接返回
  var t0 = performance.now();
  _productsCache = await getProductsAsync();   // 未命中，从 IndexedDB 读取
  console.log('[Cache] loaded ' + _productsCache.length + ' products in ' + (performance.now() - t0).toFixed(1) + 'ms');
  return _productsCache;
}
缓存依赖链：高级缓存依赖低级缓存。例如 getProductMapCached() 调用 getProductsCached()，getTokenInvertedIndexCached() 调用 getProductIndexDbCached()。首次调用时，整条依赖链会逐级填充；后续调用直接命中内存缓存，0ms 返回。
缓存失效机制

缓存必须在数据变更时主动失效，否则 UI 会读到旧数据。本系统设计了三级失效函数：

失效函数清除的缓存触发时机
invalidateCache() 全部缓存 clearAllDataAsync() 清空数据库时
invalidateProductCache() _productsCache, _indexDbCache, _productMapCache, _nameIndexCache, _tokenInvertedIndex, _pinyinCache setProductsAsync() 或 setProductPinyinAsync() 写入后
invalidateCustomerCache() _customersCache, _customerIndexDbCache, _customerMapCache, _customerTokenInvertedIndex setCustomersAsync() 或 setCustomerPinyinAsync() 写入后 
// 失效时机示例
async function setCustomersAsync(customers) {
  initDB();
  var normalized = customers.map(function(c) {
    var obj = Object.assign({}, c);
    obj.id = String(obj.id);
    return obj;
  });
  await db.customer.clear();
  await db.customer.bulkPut(normalized);
  invalidateCustomerCache();  // ← 写入后立即失效缓存
}
关键原则：写入必失效。任何修改 IndexedDB 数据的操作（setCustomersAsync、setProductsAsync、setCustomerPinyinAsync、setProductPinyinAsync、clearAllDataAsync），完成后都必须调用对应的 invalidateXxxCache()。遗漏失效会导致 UI 展示过期数据。
全量获取与5万上限约束

全量获取发生在 get_cus_pro.html 的 fetchFullData() 中，流程如下：

1
获取总记录数
调用后端 API 获取客户和产品的总数
2
5万上限检查
Math.min(total, 50000) 计算实际读取量，超限时弹出 toast 提示"总量超界，只取5万数据"
3
分批读取
按批次大小（客户1万/批，产品2万/批）循环调用后端 API，OFFSET 分页
4
兜底截断
读取完成后，若数据量仍超5万（理论上不会），slice(0, 50000) 截断
5
写入 Dexie
调用 PinyinMatch.setCustomersAsync() / PinyinMatch.setProductsAsync()，内部执行 clear() + bulkPut()
6
分批生成拼音
每批200条，调用 PinyinMatch.setCustomerPinyinAsync() / PinyinMatch.setProductPinyinAsync()
// 5万上限约束核心代码
var CUSTOMER_LIMIT = 50000;
var PRODUCT_LIMIT = 50000;

// 步骤2：计算实际读取量
var customerFetchTotal = Math.min(customerTotal, CUSTOMER_LIMIT);
var productFetchTotal = Math.min(productTotal, PRODUCT_LIMIT);
var customerBatches = Math.ceil(customerFetchTotal / CUSTOMER_BATCH_SIZE) || 1;
var productBatches = Math.ceil(productFetchTotal / PRODUCT_BATCH_SIZE) || 1;

// 步骤4：兜底截断
if (allCustomers.length > CUSTOMER_LIMIT) {
  allCustomers = allCustomers.slice(0, CUSTOMER_LIMIT);
}
if (allProducts.length > PRODUCT_LIMIT) {
  allProducts = allProducts.slice(0, PRODUCT_LIMIT);
}

// 步骤5：写入 Dexie（内部自动失效缓存）
await PinyinMatch.setCustomersAsync(allCustomers);
await PinyinMatch.setProductsAsync(allProducts);

拼音数据的事务写入

拼音生成是异步分批进行的，写入时需要逐条读取已有记录 → 更新拼音字段 → 写回。为避免中途出错导致数据不一致，使用 Dexie 事务：

async function setProductPinyinAsync(pinyinMap) {
  initDB();
  await db.transaction('rw', db.product, async function() {
    for (var id in pinyinMap) {
      var existing = await db.product.get(id);   // 主键查询
      if (existing) {
        existing.pinyin = pinyinMap[id].pinyin;
        existing.pinyin_abbr = pinyinMap[id].pinyin_abbr;
        await db.product.put(existing);     // 整条写回
      }
    }
  });
  invalidateProductCache();  // 事务完成后失效缓存
}
为什么用 put 而不是 update？Dexie 的 put() 是"整条替换"（按主键），如果记录已存在则覆盖，不存在则新增。update() 是"部分字段更新"，但要求记录必须存在。本场景中先 get() 确认存在再 put()，更安全直观。
事务的必要性：拼音写入涉及数千条记录的逐条更新。如果不用事务，中途出错会导致部分记录已更新、部分未更新的不一致状态。事务保证"要么全部成功，要么全部回滚"。
同步状态管理

sync_status 表是一个简单的键值对存储，用于记录数据同步的时间戳等元数据：

// 读取同步状态
async function getSyncStatusAsync(key) {
  initDB();
  var record = await db.sync_status.get(key);
  return record ? record.value : null;
}

// 写入同步状态
async function setSyncStatusAsync(key, value) {
  initDB();
  await db.sync_status.put({ key: key, value: value });
}
keyvalue 示例用途
sync_time"2026-05-22T10:30:00Z" 最近一次全量同步时间
incremental_time"2026-05-22T14:00:00Z" 最近一次增量同步时间（增量 API 的查询参数）
设计优势：同步状态存在 IndexedDB 而非 localStorage，与业务数据在同一数据库中，清除数据时一并清除，避免状态残留。
数据清理与重置 
async function clearAllDataAsync() {
  if (db) {
    try {
      await db.delete();  // 删除整个数据库（最彻底）
    } catch (e) {
      // 降级方案：逐表清空
      await db.customer.clear();
      await db.product.clear();
      await db.sync_status.clear();
    }
    db = null;  // 重置实例，下次 initDB() 会重新创建
  }
  invalidateCache();  // 清除全部内存缓存
}
db.delete() vs 逐表 clear()：db.delete() 会删除整个数据库文件，下次 initDB() 时需要重新声明 schema。clear() 只清空数据，保留表结构。代码中优先 delete()，失败时降级为 clear()，兼顾彻底性和兼容性。

踩坑记录与最佳实践
坑1：initDB() 返回值不是 Promise 踩坑
initDB() 返回 Dexie 实例（同步），不是 Promise。如果写 initDB().then(...) 会报 TypeError: initDB(...).then is not a function，导致整个页面脚本中断。
❌ initDB().then(function() { ... }) → 报错 ✅ PinyinMatch.init().then(function() { ... }) → 正确
坑2：id 类型不一致导致 get() 查不到 踩坑
后端返回的 id 可能是数字 123，而 Dexie 中存储的主键是字符串 "123"。如果直接用数字 id 调用 db.customer.get(123)，会查不到数据。所有写入操作内部都做了 String(obj.id) 转换，但外部查询时也需注意类型一致。
❌ db.customer.get(123) → undefined ✅ db.customer.get("123") → {id: "123", name: "..."}
坑3：bulkPut 前必须 clear 踩坑
bulkPut() 是"upsert"语义——主键存在则更新，不存在则新增。如果不先 clear()，旧数据会残留。本系统的全量获取场景要求"全量替换"，所以必须先 clear() 再 bulkPut()。
await db.customer.clear(); // 先清空 await db.customer.bulkPut(data); // 再批量写入
坑4：缓存失效遗漏 踩坑
如果直接操作 db.customer.put() 而不通过 setCustomersAsync()，缓存不会失效，UI 会展示旧数据。所有数据变更必须通过封装的 API 进行，不要绕过缓存层直接操作 Dexie。
❌ db.customer.put(newRecord) // 缓存未失效 ✅ PinyinMatch.setCustomersAsync(allData) // 自动失效缓存
坑5：5万上限必须在批次计算前生效 踩坑
如果先计算批次（Math.ceil(total / batchSize)）再截断，会导致从服务器多读数据后丢弃。正确做法是先用 Math.min(total, 50000) 计算实际读取量，再基于此计算批次。
❌ batches = Math.ceil(100000 / 10000) → 10批，多读5万条 ✅ fetchTotal = Math.min(100000, 50000) → 50000 batches = Math.ceil(50000 / 10000) → 5批，只读5万条
最佳实践总结：
① 所有 Dexie 操作通过 PinyinMatch 闭包 API 进行，UI 层不直接操作数据库
② 写入操作后必须调用对应的 invalidateXxxCache()
③ 主键 id 统一为字符串类型
④ 全量替换用 clear() + bulkPut()，部分更新用事务 transaction('rw') + get() + put()
⑤ 5万上限约束在批次计算前生效，避免多读后丢弃
⑥ 缓存层对 UI 透明，调用方无需关心数据来源
