1. 为什么"价格核算"是智能制单的关键闭环

智能制单的两大核心任务是客户/产品匹配与价格/税点核算。前者已经通过拼音 + 分词双引擎达到较高准确度，后者目前仍是空白：

现状：价格栏位的"裸露"

当甲方询价单/采购单中未提供价格时，系统在 [index.html:2080](file:///Users/guorui/同步空间/20021218/临时开发/智能制单/拼音试验/dexiedb/index.html#L2080) 处仅显示「待询价」占位，要求用户手工编辑：

<div ... onclick="editField(this,' + idx + ',\'price\')">' + (product.price || '待询价') + '</div>

这意味着：匹配做得再好，没有价格也无法生成可提交的订单。

价格核算之所以成为关键闭环，原因有三：

  1. 真实场景高频：多数甲方询价单/采购单只列产品明细和数量，价格往往要求销售自行报价
  2. 人工定价痛点深：销售凭印象报价、翻历史微信/Excel/订单系统问老板，30-60 分钟/单极为常见
  3. 报价错误代价高：报高了丢单，报低了亏利润，"凭感觉"是最不可靠的方式
22 小时/月
按 15 单/天 × 50 条/单估算，AI 定价可节省的工时
前提：客户 × 产品历史价有数据可用

但要实现这一目标，前提是把"价格数据"准备好。下面先盘点现有数据基础。

2. 现状盘点：现有数据基础与缺失

维度现状是否具备"价格定价"基础
产品表同步字段 id, pro_name, model, spec, modstm（见 pinyin_sync.js:505） ❌ 不含价格字段
客户表同步字段 id, cu_name, amstamp（见 pinyin_sync.js:396） ❌ 不含等级、VIP 标记
价格策略表 本地不存在 ❌ 需新建/对接
历史订单/报价表 订单写入时使用 amount, un_price，但未拉取历史 ⚠️ 仅本地有写入，无远端历史聚合
客户-产品对应关系 无 ❌ 需拉订单/明细聚合
VIP/大客户标签 未知 ❌ 需确认数据源
关键结论

4 种价格来源全部需要新数据接入。最轻量的是来源 ① ②（改一下同步字段即可），最重的是来源 ④（需要"客户 × 产品"二维聚合查询）。

3. 4 种价格来源详解

3.1 来源 ① — 产品表标准价

数据源product 表新增 pro_standard_price（或类似字段）
实施步骤① 同步字段加 1 列；② 写入 IndexedDB；③ UI 拉价时直接取
优点实施最简单（半天）、无额外接口
缺点对个性化报价无帮助；标准价往往高于实际成交价
准确度⭐⭐
性能⭐⭐⭐⭐⭐（本地读，毫秒级）
推荐度⭐⭐⭐ 作为兜底

3.2 来源 ② — 产品表内部结算价 + 上浮比例

数据源product 表 pro_cost_price（内部结算价）+ 用户输入上浮比例（8%、3% 等）
实施步骤① 同步字段加 1 列；② 加 1 个上浮比例输入框；③ 提交时实时计算
优点简单、有"加价率"概念，贴近 ERP 思维
缺点比例需要用户每次输入，不便；与客户无关，不够灵活
准确度⭐⭐（取决于比例设置）
性能⭐⭐⭐⭐⭐
推荐度⭐⭐ 作为补足

3.3 来源 ③ — 价格策略（VIP 大客户 × 12 种产品）

数据源价格策略表（按客户类型 × 产品 × 价格 矩阵）
实施步骤① 新建/对接价格策略表；② 增量同步到本地；③ 拉价时按 (客户类型, 产品 ID) 查表
优点业务规则清晰、配置化、便于业务侧维护
缺点只能覆盖"已被规则定义的"组合；新客户/新产品需先建策略
准确度⭐⭐⭐⭐（策略内的非常准）
性能⭐⭐⭐⭐（本地表查询）
推荐度⭐⭐⭐⭐ 核心策略

3.4 来源 ④ — 历史最近成交价（按明细粒度）

数据源历史订单/报价明细表（按 客户 ID × 产品 ID × 时间）
实施步骤① 拉订单/明细接口；② 本地构建 cu_pro_recent 索引表（按客户 ID+产品 ID 索引，取 max(时间)）；③ 同步时增量更新；④ 拉价时按 (客户 ID, 产品 ID) 查 max
优点最贴近真实成交；无需配置
缺点计算量较大（要遍历订单）；老客户没历史就空
准确度⭐⭐⭐⭐⭐（实际成交）
性能⭐⭐⭐（聚合首次慢，可缓存）
推荐度⭐⭐⭐⭐⭐ 最佳精度
为什么来源 ④"按明细颗粒度"是必要的？

用户给出的例子很典型：

当前客户是菲尔德，产品明细包含 A、B、C、D，就分别获取 A 一个月前、B 十天前的成交价。

这意味着：每个产品的"最近成交价"独立计算，互不影响。粒度必须是"客户 × 产品"，而非"客户"或"产品"。

4. 快速筛选 × 准确获取：4 来源对比

用户提出的核心目标拆解为两个子目标：

  • 快速筛选：让用户能瞬间找到"我该用哪种方式定价"
  • 准确获取：选好后拿到正确价格，不出错
来源快速筛选准确获取短板
① 标准价 0 步直接用 字段查表，100% 但不准
② 结算价+上浮 需用户填比例（慢） 计算公式 100% 比例难定
③ 价格策略 看客户是否 VIP/在策略表内 矩阵查询 100% 仅覆盖被定义产品
④ 历史价 看客户是否有历史成交 max(time) 100% 拉订单首次慢
关键洞察
  • 来源 ① ② 是"无配置时也能用"——但用户每次都要决策
  • 来源 ③ ④ 是"按场景自动命中"——最智能但需要数据基础

5. 推荐方案：一键获取 + 两段式选择（v1.1.1）

核心思想（v1.1 重大调整）：价格获取不是"自动阶梯匹配"，而是在已匹配好的明细基础上，弹出方式选择界面，由用户主动选择策略，再按需远端拉取。

v1.0 → v1.1 关键变化
  • 触发方式：从"匹配完成自动执行"改为"用户主动点击"一键获取价格"按钮"
  • 数据来源：从"本地缓存"改为"直接远端服务器拉取"
  • 前置条件：必须"全部产品已匹配完成"才能进入价格获取阶段
  • 方式选择：4 种来源 ① ② ③ ④ 改为互斥选项（用户 4 选 1），而非"阶梯自动"

  2. 第二段（条件触发）：

为什么是"动态下拉"而不是"硬编码"？
  • 策略类型可配置：业务侧可能随时新增/调整"特殊客户价""节日促销价"等类型
  • 避免前端硬编码：硬编码 5-10 个固定选项，前端每次业务调整都要发版
  • 多租户/多公司：不同分公司可能用不同策略集，下拉按需加载
  • 国际化：策略类型名称由服务端返回，支持多语言

2.4.2 上浮比例的"参考值"机制（v1.1.2 核心）

为减少用户每次重复输入，支持上浮比例的"上次值"参考：

机制实现方式用户感知
默认填充 localStorage 读取 lastUsedPriceRatio，自动填入输入框 打开浮窗，比例已是上次用值（如 8%）
快速采用 浮窗显示"上次使用：8%"快捷按钮，单击即采用 不必修改，直接单击即可
历史记录 localStorage 存最近 3-5 个使用过的比例，按时间倒序 可看到自己常用的几个比例
提交时记忆 用户确认获取时，把当前值写入 localStorage 下次打开自动用最近值
为什么需要"上次值"机制？

用户原话：

上浮百分比可能需要手工填写，也可以取上次填写的值作为参考。

这反映了两个需求：

  • 灵活性：用户希望有完全控制权，能手工输入任意值（应对非标准情况）
  • 便捷性：希望系统记住常用值，避免每次都重新填（应对日常情况）

"localStorage 默认填充 + 快捷采用按钮"同时满足这两个需求，不强制、不繁琐。

2.4.3 C 来源的"结算价 × 上浮比例"价格计算（远端回前端计算）

v1.1.2 价格计算放在前端，远端只返回原始结算价：

// v1.1.2 升级：fetchPricesByStrategy 第 3 个分支
if (strategy === 'C') {
  // 1) 远端拉取产品结算价
  var costData = await loadData({
    cmd: 'load_data',
    dtname: 'product',
    field: 'id,pro_cost_price',
    where: "id IN (" + productIds.join(',') + ") AND dflag=0 AND status=0"
  });

  // 2) 前端按用户输入的 ratio 计算最终价
  //    最终价 = pro_cost_price × (1 + ratio/100)
  return costData.map(function(row) {
    return {
      pro_id: row.id,
      pro_cost_price: row.pro_cost_price,
      // 关键：返回原值，前端按 ratio 计算后再回填
      _ratio: extraParams.ratio   // 透传比例，便于 UI 标注
    };
  });
}

2.4.4 前端回填逻辑（应用 ratio）

// 前端 applyPriceToProducts（v1.1.2 升级）
function applyPriceToProducts(remoteData, strategy, extraParams) {
  currentProducts.forEach(function(p) {
    var row = remoteData.find(function(r) { return String(r.pro_id) === String(p.matchedId); });
    if (!row) return;

    if (strategy === 'C') {
      // C 来源：按 ratio 计算
      p.price = (row.pro_cost_price * (1 + extraParams.ratio / 100)).toFixed(2);
      p._priceSource = 'costRatio';
      p._priceMeta = {
        strategy: '结算价上浮 ' + extraParams.ratio + '%',
        costPrice: row.pro_cost_price,
        ratio: extraParams.ratio,
        finalPrice: p.price
      };
    } else {
      // A / B / D 来源：直接使用远端返回的 price
      p.price = row.price;
      p._priceSource = strategy;
    }
  });

  // v1.1.2 关键：记忆本次使用的 ratio
  if (strategy === 'C' && extraParams.ratio) {
    localStorage.setItem('lastUsedPriceRatio', String(extraParams.ratio));
    // 顺带记录到历史
    var history = JSON.parse(localStorage.getItem('priceRatioHistory') || '[]');
    history = [extraParams.ratio].concat(history.filter(function(r) { return r !== extraParams.ratio; })).slice(0, 5);
    localStorage.setItem('priceRatioHistory', JSON.stringify(history));
  }
}
localStorage 记忆的两个键
  • lastUsedPriceRatio：最近一次使用的比例（单值，用于默认填充）
  • priceRatioHistory：最近使用过的 5 个比例（数组，用于快捷按钮）

数据仅存本地，不与服务器同步，符合"用户偏好"语义。

// 通用拉取接口（伪代码）
// POST /api.xt?cmd=load_data&dtname={table}&field={fields}&where={condition}
async function fetchPricesByStrategy(strategy, productIds, customerId, extraParams) {
  var params = null;
  switch (strategy) {
    case 'A':  // 价格策略（v1.1.1 升级：带 type_code 过滤）
      params = {
        dtname: 'price_strategy',
        field:  'pro_id,price',
        where:  "type_code = '" + extraParams.typeCode + "' " +
                "AND pro_id IN (" + productIds.join(',') + ")"
      };
      break;
    case 'B':  // 历史最近成交价
      params = {
        dtname: 'order_detail',
        field:  'pro_id,price,order_time,order_no',
        where:  "cu_id = " + customerId + " AND pro_id IN (" + productIds.join(',') + ")",
        orderBy: 'order_time DESC',
        groupBy: 'pro_id'  // 取每个产品最近一条
      };
      break;
    case 'C':  // 内部结算价 + 上浮比例
      params = {
        dtname: 'product',
        field:  'id,pro_cost_price',
        where:  "id IN (" + productIds.join(',') + ") AND dflag=0 AND status=0"
      };
      // 拉回后前端按用户输入的 ratio 计算
      // 最终价 = pro_cost_price × (1 + ratio/100)
      break;
    case 'D':  // 产品表标准价
      params = {
        dtname: 'product',
        field:  'id,pro_standard_price',
        where:  "id IN (" + productIds.join(',') + ") AND dflag=0 AND status=0"
      };
      break;
  }
  return await loadData(params);
}

为什么 v1.1 不再分阶段？

🏅 Phase 2（可选）— 增强体验

范围：增值能力（非阻塞）

10. 风险与边界（v1.1.1）

风险缓解策略
历史价是"特批价"，批量推送误导 UI 上显示"来源：历史成交（2025-12-15）"，让用户看时间
老客户无历史成交记录 远端返回空 → 系统提示"该客户暂无历史成交，请选用其他策略"
远端接口异常（超时/404） 捕获异常 → 提示用户"价格拉取失败，请稍后重试或手动输入"
用户每次都要选策略，操作繁琐 提供"记住上次的策略"偏好（localStorage 记忆）
价格敏感（不让销售看到别人的价） 策略 B 接口 SQL 中强制 cu_id = 当前客户，不显示其他客户
价格策略表尚无数据（Phase 1 初期） 策略 A 远端返回空 → 浮窗内提示"价格策略未配置"并禁用该选项
网络抖动导致拉取慢 loading 态 + 1 秒后提示"正在拉取，请稍候"，避免用户重复点击
策略类型字典表为空 v1.1.1 新增 第二段下拉显示"暂无可用策略类型"，并提示业务侧去后台维护
所选策略类型在 price_strategy 中无对应数据 拉取返回空 → UI 提示"该策略下未配置价格，请选用其他策略类型"
localStorage 异常（隐私模式 / 容量满） v1.1.2 新增 try-catch 包装；失败时降级为"空白输入"，不影响主流程
用户输入上浮比例 ≤ 0 或 > 100 v1.1.2 新增 前端校验，提示"比例应在 0-100 之间"，不允许提交
v1.1.2 风险面 vs v1.1.1

相比 v1.1.1，v1.1.2 新增以下风险：

  • ⚠️ localStorage 在隐私模式下不可用（浏览器兼容）
  • ⚠️ 上浮比例的取值范围需前端校验
  • ⚠️ 历史记录需考虑清空/重置机制

但带来长期收益：

  • ✅ C 来源用户操作更流畅，无需每次输入
  • ✅ 两段式机制完整覆盖需要参数补充的来源（A 和 C）
  • ✅ "上次值"作为参考，平衡灵活性与便捷性
