拼音查询性能优化方案 v2

倒排索引 + 算法优化，从6秒到亚秒级的性能飞跃
创建：2026-05-19
文件：pinyin_match2.js / index2.html
测试场景：20条产品 × 9000条产品库
1. 问题分析：为什么 index2 的缓存优化没起作用？

index2 相比 index 做了大量缓存优化（内存缓存产品数据、预建名称索引、预计算拼音），但实测20条产品明细匹配速度几乎没有差异——都需5-6秒。

根因：瓶颈不在数据查询，而在 pinyinMatch() 算法本身。缓存优化只省了约40ms的数据查询时间，但算法计算耗时约5950ms，占比99.3%。
环节indexindex2占比
Dexie数据查询~50ms~10ms0.2%
pinyinMatch 算法~5950ms~5950ms99.3%
总计~6000ms~5960ms100%

算法复杂度分析

原 pinyinMatch() 对每条查询产品，都要遍历全部产品库做4维评分：

// 每条查询 × 全量产品库 × 4维评分 × O(m×n) DP算法
for (每条查询产品) {           // 20条
  for (每条数据库产品) {       // 9000条
    calcStringSimilarity(全拼)  // O(m×n) Levenshtein + O(m×n) LCS
    calcStringSimilarity(首字母) // O(m×n) Levenshtein + O(m×n) LCS
    pinyinWordBagSimilarity()   // O(words)
    lengthScore()               // O(1)
  }
}
// 总操作量：20 × 9000 × 4 × ~900 ≈ 6.5亿次 → 5-6秒
2. 优化方案：三层优化策略
1
拼音分词倒排索引 减少候选集
将产品拼音按 _ 分词，构建 token → 产品索引的倒排索引。
查询时只对共享 token 的候选集做评分，而非全量扫描。
动态阈值：≤2词→1个token，3-4词→2个token，5-7词→3个token，8+词→40%。
2
Levenshtein 单行DP + 移除LCS 加速单次计算
单行DP：用2个一维数组交替替代 (m+1)×(n+1) 二维矩阵，内存分配减少99%。
移除LCS：LCS与Levenshtein高度冗余，去掉后 calcStringSimilarity 计算量减半。
3
降级重试兜底 保证召回率
动态阈值筛选后若候选集为空，自动降级到 minOverlap=1 重新搜索，确保不漏匹配。
3. 拼音分词倒排索引

3.1 为什么不用首字母过滤？

首字母过滤有致命缺陷——查询"不锈钢螺栓"首字母是 b，但目标"安钢不锈钢螺栓"首字母是 a，会被错误排除。

首字母过滤（错误）

  • 查询"不锈钢螺栓" → 首字母 b
  • 只保留首字母为 b 的产品
  • "安钢不锈钢螺栓"首字母 a → 被排除 ❌
  • 一个字不同就丢失匹配

分词倒排索引（正确）

  • 查询"不锈钢螺栓" → tokens [bu, xiu, gang, luo, shuan]
  • 保留共享 ≥2 个token的产品
  • "安钢不锈钢螺栓"共享5个token → 保留 ✅
  • "红色油漆"共享0个token → 排除 ✅

3.2 倒排索引结构

// 产品拼音分词后构建倒排索引
// 产品: "不锈钢螺栓" → pinyin: "bu_xiu_gang_luo_shuan"
// 分词: ["bu", "xiu", "gang", "luo", "shuan"]

invertedIndex = {
  "bu":    [0, 3, 7, 12, 45, ...],   // 包含"bu"的产品索引列表
  "xiu":   [0, 3, 7, 56, ...],        // 包含"xiu"的产品索引列表
  "gang":  [0, 2, 3, 7, 15, ...],     // 包含"gang"的产品索引列表
  "luo":   [0, 7, 89, ...],            // 包含"luo"的产品索引列表
  "shuan": [0, 7, 23, ...],            // 包含"shuan"的产品索引列表
  ...
}

// 动态阈值筛选后若候选集为空，降级到 minOverlap=1 重新搜索

}
4. 算法层优化

4.1 Levenshtein 单行DP

旧版：全矩阵DP

// 分配 (m+1)×(n+1) 二维数组
var dp = [];
for (var i = 0; i <= m; i++) { dp[i] = [i]; }
for (var j = 0; j <= n; j++) { dp[0][j] = j; }
for (var i = 1; i <= m; i++)
  for (var j = 1; j <= n; j++)
    dp[i][j] = Math.min(...)

新版：单行DP

// 只用2个一维数组交替
var prev = [], curr = [];
for (var j = 0; j <= n; j++) prev[j] = j;
for (var i = 1; i <= m; i++) {
  curr[0] = i;
  for (var j = 1; j <= n; j++)
    curr[j] = Math.min(...);
  var swap = prev; prev = curr; curr = swap;
}
效果：内存分配从 O(m×n) 降到 O(n)，减少99%的GC压力。实测单次调用提速2-3倍。

4.2 移除LCS计算

原 calcStringSimilarity 同时计算 Levenshtein 和 LCS，取平均值：

// 旧版：两个 O(m×n) DP算法
var levScore = 1 - levenshteinDistance(a, b) / maxLen;   // O(m×n)
var lcsScore = 2 * longestCommonSubsequence(a, b) / (a.length + b.length); // O(m×n)
return (levScore + lcsScore) / 2;

// 新版：只用 Levenshtein
return 1 - levenshteinDistance(a, b) / maxLen;  // O(m×n)，计算量减半
理由：LCS 和 Levenshtein 衡量的都是"字符串相似度"，高度冗余。去掉LCS对匹配准确率影响极小，但 calcStringSimilarity 计算量直接减半。每条产品原本需要调用2次 calcStringSimilarity（全拼+首字母），每次内含2个DP，共4个DP；现在每次1个DP，共2个DP——整体计算量减少50%。

7. 踩坑记录

Bug 1：早停逻辑导致全部产品匹配失败

// 错误的早停条件
if (scores.length * 0.10 < 0.45) continue;  // scores.length 范围0~1，乘0.10后最大0.10，永远 < 0.45
// → 每条记录都被跳过！全部产品显示红色

修复：移除早停逻辑。阈值0.45太低，早停几乎不会正确触发，反而引入了致命bug。

Bug 2：未导出新增函数导致"匹配中"卡死

// index2.html 调用了未导出的函数
PinyinMatch.tokenizePinyin()         // → TypeError: not a function
PinyinMatch.getMinOverlap()         // → TypeError: not a function
PinyinMatch.getCandidatesByTokenOverlap() // → TypeError: not a function

修复：在 return {} 中导出 tokenizePinyin、getMinOverlap、getCandidatesByTokenOverlap。

Bug 3：matchProductsFromRawList 缺少 products 变量

// 重构时遗漏了 getProductsCached() 调用
var productMap = await getProductMapCached();
// 缺少: var products = await getProductsCached();
var indexDb = await getProductIndexDbCached();
...
products.filter(...)  // → ReferenceError: products is not defined

修复：添加 var products = await getProductsCached();。

Bug 4：extractOrderJSON 正则截断导致嵌套JSON解析失败

// 旧正则用 [\s\S]*?\} 非贪婪匹配
/\{[\s\S]*?"customer_name"[\s\S]*?"products"[\s\S]*?\}/
// 匹配到 products 数组第一个元素的 } 就停了
// → 截取的字符串不是完整JSON → JSON.parse 报错

修复：重写 extractOrderJSON，改为大括号层级匹配——先用正则定位关键字（如 "customer_name":），找到起始 {，再逐字符扫描跟踪大括号层级，层级归零时提取完整JSON。同时使用 tryParseJSON 容错解析。

Bug 5：AI生成JSON含非法转义导致解析失败

// AI生成的产品名含未转义的反斜杠
"耐磨手套\加厚 天然橡胶"   // \加 不是合法JSON转义
"电焊手套\黄色/带内衬"     // \黄 不是合法JSON转义
// → JSON.parse 报错 → 页面一直转圈

修复：新增 cleanInvalidEscapes(str) 函数，用正则 /\\(?![\"\\\/bfnrtu])/g 将非法转义的 \ 替换为空格。新增 tryParseJSON(str) 先尝试原始解析，失败后清理非法转义再试，返回 {obj, cleaned}。extractOrderJSON 返回 cleaned 字符串，确保下游 normalizeOrderJSON 的 JSON.parse 也能成功。

Bug 6：长产品名拼音导致匹配卡顿

// 产品名含详细描述，拼音字符串极长
"线胶耐磨王手套 星宇弹力星（双层乳胶喷盐磨砂...）"
→ pinyin: 200+ 字符
// levenshteinDistance(200, 200) = 40000次运算
// 27个产品 × 数百候选 × 4维评分 = 数百万次运算 → 页面卡死

修复：在 matchProductsFromRawList 的评分循环中，对拼音字符串做截断：全拼截断120字符（约覆盖前30个汉字），首字母截断60字符。产品名的核心区分信息（品类+型号+品牌）几乎都在前30字内，截断不影响匹配准确度，但 levenshteinDistance 计算量从 200×200=40000 降至 120×120=14400，减少64%。
