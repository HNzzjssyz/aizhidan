1. 概述与设计目标

本方案把"客户/产品拼音库"的同步逻辑整合为单一智能入口，对外暴露两个能力：

  • 用户主动同步：get_cus_pro.html 提供"同步数据"按钮，一次性完成首次全量 / 后续智能判断 / 异常降级。
  • 页面自动同步：index.html 进入页面后自动检查数据新鲜度，按需触发同步，并对跨标签完成事件做出响应。
核心设计原则
  • 单按钮：UI 只有一个"同步数据"入口，零认知负担。
  • 双轨删除：客户表（物理删除）用二分法检测，产品表（dflag 软删除）依赖服务器全局过滤。
  • 三档降级：差异检测失败 → 全量；增量失败 → 全量；同步过程中允许上层静默取消。
  • 无状态共享：同步状态（sync_time、incremental_time）存于 IndexedDB，跨页面、跨标签共享。

2. 整体架构

系统由三层构成：UI 层（index.html / get_cus_pro.html）→ 共享模块（pinyin_sync.js）→ 数据层（pinyin_match.js + IndexedDB + HTTP）。

index.html ── hooks ──→ PinyinSync.autoSyncIfNeeded() ──→ PinyinSync.sync() ↑ │ │ onSyncComplete ▼ └────────────────────────────────────────────── fetchFullData() / incrementalSync() │ │ ▼ ▼ defaultGeneratePinyin() setSyncStatusAsync() get_cus_pro.html ── 同样调用 PinyinSync.sync() ──→ 完成 / 取消 / 失败均广播 BroadcastChannel

3. 智能决策：判断增量还是全量

同步策略选择遵循 "首次强制全量 → 差异率阈值 → 异常降级" 三段式：

启动 PinyinSync.sync() │ ├─ 读 incremental_time ── null/未设置 ──→ 【策略：全量】 fetchFullData() │ │ │ └─→ 写 sync_time + incremental_time │ └─ 已设置 ──→ detectSyncStrategy() │ ├─ 拉远端 ID 列表（customer + product） ├─ 读取本地 ID 集合 ├─ 计算 missingOnLocal / extraOnLocal │ ├─ 远端 < 1000 条 ──→ 【跳过差异检测，强制全量】 │ └─ 差异率 = (missing + extra) / 远端总数 │ ├─ > 20% ──→ 【策略：全量】 fetchFullData() │ └─ ≤ 20% ──→ 【策略：增量】 incrementalSync(decision)

3.1 差异检测函数 detectSyncStrategy()

核心实现位于 pinyin_sync.js 的 detectSyncStrategy()。要点：

// 1. 拉远端所有 ID（分页，pageSize = 5000）
const customerServerIds = await fetchServerIds('customer');
const productServerIds = await fetchServerIds('product');

// 2. 远端过小（< 1000）→ 跳过检测，强制全量
if (customerServerIds.length < MIN_IDS_FOR_DIFF_CHECK &&
    productServerIds.length < MIN_IDS_FOR_DIFF_CHECK) {
  return { strategy: 'full', diffRate: 1, ... };
}

// 3. 本地 ID 集合（统一 String 化，与 IndexedDB 一致）
const customerLocalIds = new Set(localCustomers.map(c => String(c.id)));
const productLocalIds  = new Set(localProducts.map(p  => String(p.id)));

// 4. 计算差异（取数量较大的表为主表）
const useCustomer = customerServerIds.length >= productServerIds.length;
const serverIds   = useCustomer ? customerServerIds : productServerIds;
const localIds    = useCustomer ? customerLocalIds  : productLocalIds;

const serverIdSet   = new Set(serverIds.map(id => String(id)));
const missingOnLocal = serverIds.filter(id => !localIds.has(String(id)));
const extraOnLocal   = [...localIds].filter(id => !serverIdSet.has(id));

// 5. 客户/产品各自的 extra / missing（用于本地合并）
const extraOnLocalCustomers   = [...customerLocalIds].filter(id => !customerServerSet.has(id));
const extraOnLocalProducts    = [...productLocalIds].filter(id => !productServerSet.has(id));
...

// 6. 计算差异率，超过阈值则切全量
const diffRate = (missing.length + extra.length) / serverIds.length;
return diffRate > 0.2 ? { strategy: 'full', ... } : { strategy: 'incremental', ... };

3.2 决策常量

常量默认值说明
DIFF_RATE_THRESHOLD0.2差异率超过 20% 切全量
ID_FETCH_PAGE_SIZE5000远端 ID 拉取分页
MIN_IDS_FOR_DIFF_CHECK1000远端过小时跳过检测

4. 客户表同步逻辑（物理删除）

业务事实
客户表（customer）允许物理删除，无删除日志。一旦远端执行 DELETE，本地 ID 即变成"僵尸数据"，常规增量无法察觉。

同步过程由 incrementalSync(decision, hooks) 协调：

4.1 拉取阶段（时间戳 + 缺失 ID）

const lastTime = await PinyinMatch.getSyncStatusAsync('incremental_time');

// 1) 按 amstamp > lastTime 拉取变化数据
const list = await fetchModifiedByTime('customer', 'id,cu_name,amstamp',
  `amstamp > '${lastTime}'`);
const customerModified = list.map(item => ({
  id: item.id, name: item.cu_name, amstamp: item.amstamp
}));

// 2) 远端物理删除的客户
//    - decision.extraOnLocal = 本地有、远端无的 ID 集合
//    - 物理删除后远端不再返回，差异检测将其归入 extraOnLocal

4.2 合并阶段：mergeCustomers()

合并算法：

// 1) 以本地客户表为基线
const customerMap = {};
existingCustomers.forEach(c => { customerMap[String(c.id)] = c; });

// 2) 用时间戳拉取的新数据覆盖（同 ID 替换）
customerModified.forEach(c => { customerMap[String(c.id)] = c; });

// 3) 物理删除：清空 decision.extraOnLocal 中的 ID
let deletedCount = 0;
(decision.extraOnLocal || []).forEach(id => {
  const key = String(id);
  if (customerMap[key] !== undefined) { delete customerMap[key]; deletedCount++; }
});

const merged = Object.values(customerMap);

// 4) 上限保护：超过 50000 条时截断
if (merged.length > 50000) merged = merged.slice(0, 50000);

await PinyinMatch.setCustomersAsync(merged);

4.3 物理删除检测：findMissingIds()（独立工具）

虽然实际生产环境直接消费 decision.extraOnLocal，但 findMissingIds() 函数作为独立工具保留：

function findMissingIds(serverIds, localIds, lo = 0, hi = serverIds.length - 1) {
  const missing = [];
  // 终止条件：区间足够小时逐个对比
  if (lo > hi || hi - lo < 10) {
    for (let i = lo; i <= hi; i++) {
      if (!localIds.has(String(serverIds[i]))) missing.push(serverIds[i]);
    }
    return missing;
  }
  // 二分中点
  const mid = (lo + hi) >> 1;
  if (localIds.has(String(serverIds[mid]))) {
    // 中点存在 → 重点查右侧
    return [...findMissingIds(serverIds, localIds, mid + 1, hi),
            ...findMissingIds(serverIds, localIds, lo, mid - 1)];
  } else {
    // 中点缺失 → 整段都可疑
    return [serverIds[mid],
            ...findMissingIds(serverIds, localIds, lo, mid - 1),
            ...findMissingIds(serverIds, localIds, mid + 1, hi)];
  }
}
算法复杂度
二分法理论复杂度 O(n)，但实际通过"存在性剪枝"避免对完整区间逐个扫描；最坏情况下退化为 O(n)，与直接扫描相当。

5. 产品表同步逻辑（dflag 软删除 + status 停售过滤）

业务事实（v1.1 修正）
产品表（product）不允许物理删除，采用 dflag 软删除。dflag=1 表示已删除（回收站），dflag=0 表示正常。另外 status=0 表示在售，status=1 表示停售。

重要：服务器 load_data 接口不会自动追加 dflag / status 过滤条件。客户端必须在 where 中显式写 dflag=0 AND status=0，否则会把回收站数据和停售产品一起同步到本地 pinyin 库，导致做单员看到已删/已停售的产品。

5.1 拉取阶段（与客户对称）

const list = await fetchModifiedByTime('product', 'id,pro_name,model,spec,modstm',
  `modstm > '${lastTime}' AND dflag=0 AND status=0`);

// 客户端拼出的最终 SQL（示意）：
//   SELECT id,pro_name,model,spec,modstm
//   FROM product
//   WHERE modstm > '...' AND dflag=0 AND status=0
//                                       ↑ 客户端显式追加，服务端不再二次过滤

5.2 合并阶段：mergeProducts()

与 mergeCustomers() 同构，区别在于：

  • 删除依据是 decision.extraOnLocalProducts
  • 产品字段含 model 和 spec，需在 id 一致时用最新值覆盖
  • 删除触发场景：远端 dflag=1 → 客户端 dflag=0 过滤 → 远端不再返回 → 差异检测归入 extraOnLocal
  • 上/下架触发场景：远端 status 从 0 改 1（停售）→ 客户端 status=0 过滤 → 远端不再返回 → 同样归入 extraOnLocal

5.3 客户 vs 产品 同步差异表

维度客户表（物理删除）产品表（dflag 软删除 + status 停售）
远端删除方式DELETE 语句UPDATE product SET dflag=1
远端停售方式—（无此状态）UPDATE product SET status=1
远端是否会返回已删不返回已删/已停售不返回（dflag=0 AND status=0 客户端过滤）
拉取字段是否含 dflag / status否否（拉了也只会被客户端过滤）
where 是否显式含 dflag / status否是（dflag=0 AND status=0）
本地清理依据extraOnLocal（远端物理删除）extraOnLocalProducts（远端 dflag=1 或 status=1）
是否需要二分法是（保留工具函数）否
是否需要时间戳是（amstamp）是（modstm）

6. 拼音生成流程

拼音生成在数据合并之后、sync_time 写入之前执行，是同步流程的最后一步数据加工。

6.1 默认实现 defaultGeneratePinyin()

位于 pinyin_sync.js，调用方未传 hooks.generatePinyin 时自动启用：

async function defaultGeneratePinyin(info) {
  const cp = await PinyinMatch.getCustomerPinyinAsync();
  const pp = await PinyinMatch.getProductPinyinAsync();
  let newCount = 0, updateCount = 0, skippedCount = 0;
  let deletedCCount = 0, deletedPCount = 0;

  // 1) 清理已删除的拼音
  (info.deletedCustomerIds || []).forEach(id => {
    if (cp[String(id)] !== undefined) { delete cp[String(id)]; deletedCCount++; }
  });
  (info.deletedProductIds || []).forEach(id => {
    if (pp[String(id)] !== undefined) { delete pp[String(id)]; deletedPCount++; }
  });

  // 2) 客户：跳过 name 未变
  (info.customerModified || []).forEach(c => {
    const key = String(c.id);
    const existing = cp[key];
    if (existing && existing.name === (c.name || '')) { skippedCount++; return; }
    const py = PinyinMatch.generatePinyinForText(c.name || '');
    if (!existing) newCount++; else updateCount++;
    cp[key] = { id: c.id, name: c.name, pinyin: py.full, pinyin_abbr: py.abbr };
  });

  // 3) 产品：拼接 name + model + spec（过滤 placeholder）
  (info.productModified || []).forEach(p => {
    const key = String(p.id);
    const existing = pp[key];
    if (existing && existing.name === p.name &&
        existing.model === (p.model || '') && existing.spec === (p.spec || '')) {
      skippedCount++; return;
    }
    const parts = [p.name, p.model, p.spec]
      .filter(s => s && !PinyinMatch.isPlaceholder(s));
    const py = PinyinMatch.generatePinyinForText(parts.join(' '));
    if (!existing) newCount++; else updateCount++;
    pp[key] = { id: p.id, name: p.name, model: p.model || '', spec: p.spec || '',
                 pinyin: py.full, pinyin_abbr: py.abbr };
  });

  // 4) 写回（仅在有变化时）
  if (newCount + updateCount + deletedCCount + deletedPCount > 0) {
    await PinyinMatch.setCustomerPinyinAsync(cp);
    await PinyinMatch.setProductPinyinAsync(pp);
  }
}

6.2 优化要点

优化说明
跳过未变项 客户：existing.name === new.name；产品：existing.name/model/spec 三项都未变 → 跳过 pinyin-pro 调用
仅在变化时写回 newCount + updateCount + deletedCCount + deletedPCount > 0 时才触发 setCustomerPinyinAsync，避免无谓 IO
String 化 key 所有 ID 统一用 String(id) 作为 key，与 IndexedDB 存储格式一致

7. 自动同步触发机制

自动同步在 index.html 初始化时挂载，由 PinyinSync.autoSyncIfNeeded() 驱动：

7.1 触发入口

PinyinMatch.init().then(() => {
  refreshPinyinStatus();
  initCozeSDK();
  PinyinSync.init();
  PinyinSync.onSyncComplete(info => { /* 失效缓存 + 刷新 UI */ });

  // 2 秒后启动自动同步（让 UI 先稳定）
  setTimeout(() => {
    PinyinSync.autoSyncIfNeeded({
      thresholdHours: 1,
      hooks: { onLog, onToast }
    }).then(r => {
      // 不论 skipped 与否都刷新一次
      refreshPinyinStatus();
      if (!r.skipped) showToast('数据已自动同步', 'success');
    });
  }, 2000);
});

7.2 决策逻辑

PinyinSync.autoSyncIfNeeded({ thresholdHours: 1 }) │ ├─ 读 sync_time │ │ │ ├─ null（首次）──────────→ PinyinSync.sync({ silent: true }) → { skipped: false, reason: 'first_time' } │ │ │ └─ 有值 │ │ │ ├─ ageHours < 1 ──→ { skipped: true, reason: 'fresh', ageHours } │ │ │ └─ ageHours ≥ 1 ──→ PinyinSync.sync({ silent: true }) → { skipped: false, reason: 'stale' } │ └─ 返回结果给调用方决定是否显示 Toast

7.3 静默模式 silent: true

自动同步场景下，用户没有主动点击，所以：

  • 不显示 progressOverlay（避免视觉干扰）
  • 不显示"取消"按钮（用户没主动操作）
  • 日志只输出到 console（console.log('[auto-sync]', msg)）
  • 完成后通过 Toast 短暂通知

7.4 时间显示

refreshPinyinStatus() 读取 sync_time 后做时区安全的格式化：

const lastSync = await PinyinMatch.getSyncStatusAsync('sync_time');
if (lastSync) {
  // toISOString() 输出的是 UTC，加 'Z' 让 Date 解析为 UTC
  const utcTime = lastSync.replace(' ', 'T') + 'Z';
  const ageMs   = Date.now() - new Date(utcTime).getTime();
  const ageMin  = Math.floor(ageMs / 60000);
  const ageStr  = ageMin < 1 ? '刚刚'
                : ageMin < 60 ? ageMin + ' 分钟前'
                : ageMin < 24 * 60 ? Math.floor(ageMin / 60) + ' 小时前'
                : Math.floor(ageMin / (60 * 24)) + ' 天前';
}
时区陷阱
new Date("2024-01-01 12:00:00") 不带 Z 时按本地时间解析；存储的 sync_time 是 toISOString() 的 UTC 时间，必须显式加 Z 才能正确显示"X 前"。

8. 跨标签页广播机制

当用户在 A 标签页触发同步时，B 标签页应能立即知道并刷新缓存。本方案用 BroadcastChannel 实现跨标签通知。

8.1 事件类型

事件触发时机接收方典型动作
sync_started syncData 进入临界区时 显示加载提示，标记 busy
sync_complete 同步成功（含全量/增量/降级） 失效缓存、刷新状态卡、Toast 通知
sync_error 同步抛异常 Toast 错误提示
sync_finished syncData 的 finally 块 解除 busy 标记

8.2 双触发机制（关键）

陷阱
BroadcastChannel.onmessage 不会在发送方标签触发。如果只在发送方调用 broadcast()，同标签的 onSyncComplete 监听器永远收不到事件，导致 UI 不刷新。

解决方案：每次 broadcast() 时同时调用 emitLocal()，让本地监听器也能收到事件。

// pinyin_sync.js
function emitLocal(msg) {
  if (msg.type === 'sync_complete' || msg.type === 'sync_started' ||
      msg.type === 'sync_error'    || msg.type === 'sync_finished') {
    _listeners.forEach(l => { try { l(msg); } catch (e) {} });
  }
}

function broadcast(msg) {
  if (_channel && _channelSupported) {
    try { _channel.postMessage(msg); } catch (e) {}
  }
}

// syncData 中
emitLocal({ type: 'sync_complete', strategy: 'full' });
broadcast({ type: 'sync_complete', strategy: 'full' });

8.3 时序图

【场景 1：同标签自动同步】 [index.html] setTimeout ─→ autoSyncIfNeeded ─→ syncData ├─ emitLocal('sync_started') → 本地 listener 触发 ├─ broadcast('sync_started') → 其他标签 ├─ ... 拉数据 / 合并 / 拼音 └─ emitLocal('sync_complete') → 本地 listener 触发 └─ refreshPinyinStatus() ✓ 【场景 2：跨标签同步】 [A 标签：get_cus_pro.html 同步] ──→ broadcast('sync_complete') [B 标签：index.html 监听中] ──→ BroadcastChannel.onmessage └─ _listeners.forEach(触发) → refreshPinyinStatus() ✓ 【场景 3：两个标签同时触发】 [A 标签] syncData 进入临界区 → emitLocal('sync_started') → 本地 _syncing=true → broadcast('sync_started') [B 标签] 收到 broadcast → emitLocal('sync_started') → 本地 _syncing=true → 注册的 onSyncComplete 监听器 [A 标签] _syncing 已经为 true 防止重复触发

9. 异常降级链

同步过程中的任何异常都会被捕获，并尝试更"重"的策略重新执行：

syncData() │ ├─ detectSyncStrategy() 抛异常 ──→ 降级为 fetchFullData() 返回 { reason: 'detect_failed' } │ ├─ incrementalSync() 抛异常 ──→ 降级为 fetchFullData() 返回 { reason: 'incremental_failed' } │ ├─ fetchFullData() 抛异常 ──→ 返回 { ok: false, error: e.message } emitLocal('sync_error') │ └─ 网络断开 / 401 / 500 ──→ hooks.onLog + console.error + Toast

9.1 降级原因传递

所有降级路径都会在返回对象里带上 reason 字段，便于上层判断与提示：

// 全量（用户手动）  → { strategy: 'full' }
// 全量（差异率过高）→ { strategy: 'full', diffRate: 0.35 }
// 全量（首次）     → { strategy: 'full' }
// 全量（差异检测失败）→ { strategy: 'full', reason: 'detect_failed' }
// 全量（增量失败）  → { strategy: 'full', reason: 'incremental_failed' }
// 增量           → { strategy: 'incremental', diffRate: 0.05 }

10. 边缘场景与守卫

场景处理方式
并发触发（用户多点按钮 + 自动同步） _syncing 锁 + 跨标签 broadcast；二次调用返回 { ok: false, reason: 'already_syncing' }
远端 ID 列表小于 1000 跳过差异检测，强制全量（避免小数据集下差异率失真）
客户/产品总数超过 50000 截断到 50000 条（上限保护，避免 IndexedDB 容量问题）
浏览器不支持 BroadcastChannel 降级为纯本地事件，跨标签联动失效但不影响主流程
IndexedDB 写失败（容量满、并发） 异常上抛 → fetchFullData 的 try/catch → 返回 { ok: false, error } + Toast
首次访问（无 sync_time） 直接全量；完成后写入 sync_time 和 incremental_time
拼音库升级后重生成 通过清空数据按钮触发 clearAllData()，下次同步会走全量且生成拼音
页面后台 → 切换回前台 window.addEventListener('focus', refreshPinyinStatus) 重新拉时间

11.2 返回对象字段

字段类型说明
okboolean同步是否成功（即便降级也返回 true）
strategystring'full' / 'incremental' / 'full_fallback'
customersnumber合并后客户总数
productsnumber合并后产品总数
diffRatenumber差异率（仅 detectSyncStrategy 触发时有值）
reasonstring'detect_failed' / 'incremental_failed' / 'first_time' / 'fresh' / 'stale'
errorstring异常信息（仅失败时有值）

12. 未来改进

改进项说明优先级
拼音生成并发 目前是串行遍历，可拆为 200 条/批 + await new Promise(r => setTimeout(r, 0)) 让出主线程 中
增量字段白名单 目前客户/产品的 modified 列表只含必要字段，跨表更新需扩展 低
Service Worker 后台同步 使用 Background Sync API，在用户关闭页面后仍能同步 低
同步进度事件 目前 onProgress 只发"批次"信息，可加 ETA / 速率 / 阶段 中
差异检测缓存 每次都重新拉远端 ID，可缓存上次的 ID 列表减少请求 低
