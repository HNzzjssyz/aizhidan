大数据量分片分批读取方案

SaaS多租户模式下，解决单表数据量无上限导致的读取负载过高问题
创建：2026-05-20
架构：SaaS多租户 / 每租户独立MySQL库
接口：load_data (limit + start)
模块：get_cus_pro.html / pinyin_match2.js
1. 问题背景

A SaaS多租户架构（每租户独立数据库）

系统采用SaaS多租户模式，每个租户拥有独立的MySQL数据库，租户间数据完全物理隔离。不同租户的数据量差异极大：

租户类型客户表数据量产品表数据量典型场景
小型租户100 ~ 2,000200 ~ 5,000初创企业、个体商户
中型租户2,000 ~ 10,0005,000 ~ 10,000区域经销商、中型贸易商
大型租户10,000 ~ 50,00010,000 ~ 100,000全国性企业、连锁集团
超大型租户50,000+100,000 ~ 300,000行业龙头、海量SKU场景
数据量特征：一般租户的产品数量在 10,000 左右；超大型租户（大包）产品数量可达 10万~30万。为保障系统可用性，客户表和产品表各设置 5万 为硬性上限，超出时自动截断。

B 当前全量读取的灾难性后果

当前 get_cus_pro.html 的全量获取逻辑，一次请求拉取全部数据：

灾难性场景

当超大型租户（大包）的产品表达到 10万~30万 条记录时，一次全量读取会产生以下问题：

1. 数据库负载飙升 — MySQL 单次查询返回 20万+ 行，占用大量 buffer pool，虽然每租户独立数据库不影响其他租户，但会导致该租户自身的其他查询严重变慢。

2. 网络传输超时 — 20万行产品数据（含 field: id, pro_name, model, spec, modstm）约 60~100MB JSON，传输耗时可能超过 60 秒，触发浏览器或网关超时。

3. 前端内存溢出 — 浏览器一次性接收并解析 100MB JSON，内存峰值可能超过 1GB，导致页面卡死甚至崩溃。

4. 拼音生成阻塞 — 对 20万条记录逐一生成拼音，主线程阻塞 60~120 秒，用户无法操作。

2. 接口能力确认

经查阅 load_data 接口文档，确认该接口已原生支持分页参数：

参数类型说明示例
limit Number 限制返回数量，如指定 100 只返回 100 条 "limit": 10000
start Number 指定开始位置（偏移量），用于分页 "start": 10000（从第10001条开始）
flag Number flag=1 返回数据库原始值，跳过字段函数处理 "flag": 1
结论：load_data 接口已完整支持 limit + start 分页参数，无需后端改造即可实现分批读取。同时支持 "field": "count(1) cnt" 获取总记录数，用于计算分片数量。

分页查询示例

// 第1批：从第0条开始，取10000条
{
  "cmd": "load_data",
  "dtname": "product",
  "field": "id,pro_name,model,spec,modstm",
  "flag": 1,
  "limit": 10000,
  "start": 0
}

// 第2批：从第10000条开始，取10000条
{
  "cmd": "load_data",
  "dtname": "product",
  "field": "id,pro_name,model,spec,modstm",
  "flag": 1,
  "limit": 10000,
  "start": 10000
}

// 获取总记录数
{
  "cmd": "load_data",
  "dtname": "product",
  "field": "count(1) cnt",
  "flag": 1
}
// 返回：{ "ok": 1, "data": [{ "cnt": "128760" }] }
3. 方案设计

3.1 核心思路

分片读取 + 分批生成拼音：将一次全量读取拆分为多个小批次，每批读取固定数量的记录，读完后立即生成该批次的拼音，再读取下一批。通过 limit + start 参数控制每批数据量，确保单次数据库查询和前端处理的负载都在可控范围内。

3.2 分片规格

根据数据特征和性能考量，设定以下分片规格：

数据表dtname每批读取量（limit）分片依据
客户表 customer 10,000 条/批 客户数据字段少（id, cu_name, amstamp），单条体积小，1万条约 1~2MB
产品表 product 20,000 条/批 产品数据字段多（id, pro_name, model, spec, modstm），但2万条约 5~8MB，仍在可控范围
分片规格选择依据：
① limit + start 本质是 OFFSET ... LIMIT 分页，offset 过大时 MySQL 需要扫描并跳过前面所有行，性能会退化。因此每批数量不宜过小（避免批次过多），也不宜过大（避免单次负载过高）。
② 客户表字段少、单条体积小，1万条/批是安全值；产品表字段多但2万条/批的响应体积仍在 10MB 以内。
③ 对于绝大多数中小租户（客户 <1万，产品 <2万），只需 1 批即可完成全量读取，与现有体验一致。

3.3 全量获取流程

1
获取总记录数
调用 load_data 接口，field: "count(1) cnt"，获取客户表和产品表的总记录数。
根据总记录数和分片规格计算需要多少批次。
2
分批读取客户数据
按 limit=10000 分批读取客户数据，每批使用 start 偏移量递进。
每批读取完成后，立即写入 IndexedDB，并生成该批次的拼音索引。
批次间插入 await new Promise(r => setTimeout(r, 100)) 让出主线程，避免 UI 冻结。
3
分批读取产品数据
按 limit=20000 分批读取产品数据，逻辑与客户数据相同。
每批读取完成后，立即写入 IndexedDB，并生成该批次的拼音索引。
4
完成同步
所有批次读取和拼音生成完成后，更新同步时间戳，刷新 UI 状态。
显示总计：客户 N 条（M 批）、产品 K 条（L 批）。

3.4 总量上限约束

在全量获取流程的第1步（获取总记录数）之后，立即检查数据量是否超过硬性上限，超出时自动截断：

数据表硬性上限超界行为
客户表 50,000 条 超出时自动截断为前 50,000 条，弹出 toast 提示"总量超界，只取5万数据"
产品表 50,000 条 超出时自动截断为前 50,000 条，弹出 toast 提示"总量超界，只取5万数据"
总量上限约束逻辑：获取总记录数后，如果客户数 > 50,000 或产品数 > 50,000，弹出 toast 提示"总量超界，只取5万数据"，同时写入操作日志。数据收集完成后，使用 slice(0, 50000) 截断再写入 IndexedDB，保障数据库中客户和产品的最大条数不超过各5万条。增量获取合并后同样执行截断检查。 
var CUSTOMER_LIMIT = 50000;
var PRODUCT_LIMIT = 50000;

async function checkDataBounds(customerTotal, productTotal) {
  var warnings = [];
  if (customerTotal > CUSTOMER_LIMIT) {
    warnings.push('客户数据 ' + customerTotal.toLocaleString() + ' 条，超出上限 ' + CUSTOMER_LIMIT.toLocaleString() + ' 条，只取前 ' + CUSTOMER_LIMIT.toLocaleString() + ' 条');
  }
  if (productTotal > PRODUCT_LIMIT) {
    warnings.push('产品数据 ' + productTotal.toLocaleString() + ' 条，超出上限 ' + PRODUCT_LIMIT.toLocaleString() + ' 条，只取前 ' + PRODUCT_LIMIT.toLocaleString() + ' 条');
  }
  if (warnings.length > 0) {
    showToast('总量超界，只取5万数据', 'error');
    warnings.forEach(function(w) { log(w, 'info'); });
    log('总量超界，只取5万数据', 'info');
  }
  return true;
}

// 全量获取后截断
if (allCustomers.length > CUSTOMER_LIMIT) {
  allCustomers = allCustomers.slice(0, CUSTOMER_LIMIT);
}
if (allProducts.length > PRODUCT_LIMIT) {
  allProducts = allProducts.slice(0, PRODUCT_LIMIT);
}

// 增量获取合并后截断
if (merged.length > CUSTOMER_LIMIT) {
  merged = merged.slice(0, CUSTOMER_LIMIT);
}

3.5 增量获取流程

增量获取的数据量通常很小（每日新增/修改几十到几百条），不需要分片，保持现有逻辑即可。但需增加一个前置检查：

增量获取安全阈值：如果增量返回的记录数超过 5,000 条（可能是首次使用或长时间未同步），自动切换为全量分片获取模式，避免一次性处理过多增量数据。
4. 改造前后对比

改造前：全量一次读取

  • 一次请求拉取全部数据，无 limit/start
  • 20万条产品 → 单次响应 60~100MB
  • 数据库单次查询返回全部行，该租户自身其他查询严重变慢
  • 前端一次性解析大 JSON，内存峰值 1GB+
  • 拼音生成阻塞主线程 60~120 秒
  • 每租户独立数据库，不影响其他租户，但自身体验极差
  • 可能触发浏览器/网关超时

改造后：分片分批读取

  • 分批请求，每批 limit 控制数据量
  • 20万条产品 → 10批 × 2万条，每批 5~8MB
  • 数据库每次查询返回固定行数，该租户自身负载可控
  • 前端逐批解析，内存峰值降至 50MB 以内
  • 拼音生成分批执行，批次间让出主线程
  • 每租户独立数据库，完全不影响其他租户
  • 不会超时，进度条实时反馈

不同数据量下的批次计算

5. 详细实现

5.1 获取总记录数 

async function getTotalCount(dtname) {
  var params = {
    cmd: 'load_data',
    dtname: dtname,
    field: 'count(1) cnt',
    flag: 1
  };
  var data = await sendLoadData(params);
  if (data.ok === 1 && data.data && data.data[0]) {
    return parseInt(data.data[0].cnt, 10);
  }
  return 0;
}

5.2 分片分批全量获取 

var CUSTOMER_BATCH_SIZE = 10000;
var PRODUCT_BATCH_SIZE = 20000;

async function fetchFullDataBatched() {
  showProgressOverlay();

  // Step 1: 获取总记录数
  showProgress('正在统计记录数...', 0, 1, '查询客户表...');
  var customerTotal = await getTotalCount('customer');
  showProgress('正在统计记录数...', 0, 1, '查询产品表...');
  var productTotal = await getTotalCount('product');

  var customerFetchTotal = Math.min(customerTotal, CUSTOMER_LIMIT);
  var productFetchTotal = Math.min(productTotal, PRODUCT_LIMIT);
  var customerBatches = Math.ceil(customerFetchTotal / CUSTOMER_BATCH_SIZE) || 1;
  var productBatches = Math.ceil(productFetchTotal / PRODUCT_BATCH_SIZE) || 1;
  var totalBatches = customerBatches + productBatches;
  var completedBatches = 0;

  log('记录统计：客户 ' + customerTotal + ' 条（取 ' + customerFetchTotal + ' 条，' + customerBatches + ' 批），产品 ' + productTotal + ' 条（取 ' + productFetchTotal + ' 条，' + productBatches + ' 批）', 'info');

  // Step 1.5: 超界检查与截断
  var boundsOk = await checkDataBounds(customerTotal, productTotal);

  // Step 2: 分批读取客户数据
  var allCustomers = [];
  for (var ci = 0; ci < customerBatches; ci++) {
    var start = ci * CUSTOMER_BATCH_SIZE;
    showProgress(
      '读取客户数据...',
      completedBatches, totalBatches,
      '第 ' + (ci + 1) + '/' + customerBatches + ' 批（start=' + start + ', limit=' + CUSTOMER_BATCH_SIZE + '）'
    );

    var params = {
      cmd: 'load_data',
      dtname: 'customer',
      field: 'id,cu_name,amstamp',
      flag: 1,
      limit: CUSTOMER_BATCH_SIZE,
      start: start
    };
    var data = await sendLoadData(params);
    var list = parseLoadDataResponse(data);
    var normalized = list.map(function(item) {
      return { id: item.id, name: item.cu_name || item.name || '' };
    });
    allCustomers = allCustomers.concat(normalized);

    completedBatches++;
    await new Promise(function(r) { setTimeout(r, 100); });
  }

  // 写入客户数据并生成拼音（超限截断）
  if (allCustomers.length > CUSTOMER_LIMIT) {
    allCustomers = allCustomers.slice(0, CUSTOMER_LIMIT);
  }
  await PinyinMatch.setCustomersAsync(allCustomers);
  await generatePinyinForType('customer', allCustomers);
  log('客户数据写入完成：' + allCustomers.length + ' 条', 'ok');

  // Step 3: 分批读取产品数据
  var allProducts = [];
  for (var pi = 0; pi < productBatches; pi++) {
    var start = pi * PRODUCT_BATCH_SIZE;
    showProgress(
      '读取产品数据...',
      completedBatches, totalBatches,
      '第 ' + (pi + 1) + '/' + productBatches + ' 批（start=' + start + ', limit=' + PRODUCT_BATCH_SIZE + '）'
    );

    var params = {
      cmd: 'load_data',
      dtname: 'product',
      field: 'id,pro_name,model,spec,modstm',
      flag: 1,
      limit: PRODUCT_BATCH_SIZE,
      start: start
    };
    var data = await sendLoadData(params);
    var list = parseLoadDataResponse(data);
    var normalized = list.map(function(item) {
      return {
        id: item.id,
        name: item.pro_name || item.name || '',
        model: item.model || '',
        spec: item.spec || ''
      };
    });
    allProducts = allProducts.concat(normalized);

    completedBatches++;
    await new Promise(function(r) { setTimeout(r, 100); });
  }

  // 写入产品数据并生成拼音（超限截断）
  if (allProducts.length > PRODUCT_LIMIT) {
    allProducts = allProducts.slice(0, PRODUCT_LIMIT);
  }
  await PinyinMatch.setProductsAsync(allProducts);
  await generatePinyinForType('product', allProducts);
  log('产品数据写入完成：' + allProducts.length + ' 条', 'ok');

  // Step 4: 更新同步时间戳
  var now = new Date().toISOString().replace('T', ' ').substring(0, 19);
  await PinyinMatch.setSyncStatusAsync('sync_time', now);
  await PinyinMatch.setSyncStatusAsync('incremental_time', now);

  hideProgressOverlay();
  await updateStatus();
  await renderCurrentTab();
  showToast('数据获取完成：客户 ' + allCustomers.length + ' 条，产品 ' + allProducts.length + ' 条', 'success');
}

5.3 分批拼音生成 

var PINYIN_BATCH_SIZE = 200;

async function generatePinyinForType(type, items) {
  var pinyinMap = {};
  var total = items.length;

  for (var idx = 0; idx < total; idx += PINYIN_BATCH_SIZE) {
    var end = Math.min(idx + PINYIN_BATCH_SIZE, total);

    for (var i = idx; i < end; i++) {
      var item = items[i];
      var text = type === 'customer'
        ? item.name
        : [item.name, item.model, item.spec]
            .filter(function(s) { return !PinyinMatch.isPlaceholder(s); })
            .join(' ');

      var py = PinyinMatch.generatePinyinForText(text);
      pinyinMap[item.id] = {
        id: item.id,
        name: item.name,
        pinyin: py.full,
        pinyin_abbr: py.abbr
      };
      if (type === 'product') {
        pinyinMap[item.id].model = item.model || '';
        pinyinMap[item.id].spec = item.spec || '';
      }
    }

    showProgress(
      '生成' + (type === 'customer' ? '客户' : '产品') + '拼音...',
      end, total,
      '已完成 ' + Math.round(end / total * 100) + '%'
    );

    if (idx + PINYIN_BATCH_SIZE < total) {
      await new Promise(function(r) { setTimeout(r, 50); });
    }
  }

  if (type === 'customer') {
    await PinyinMatch.setCustomerPinyinAsync(pinyinMap);
  } else {
    await PinyinMatch.setProductPinyinAsync(pinyinMap);
  }
  log((type === 'customer' ? '客户' : '产品') + '拼音生成完成：' + Object.keys(pinyinMap).length + ' 条', 'ok');
}

5.4 增量获取安全阈值 

var INCREMENTAL_THRESHOLD = 5000;

async function fetchIncrementalDataSafe() {
  var lastTime = await PinyinMatch.getSyncStatusAsync('incremental_time');
  if (!lastTime) {
    showToast('尚未进行过全量获取，请先全量获取', 'warning');
    return;
  }

  // 先用 count 探测增量数据量
  var customerWhere = "amstamp > '" + lastTime + "'";
  var productWhere = "modstm > '" + lastTime + "'";

  var cCountParams = { cmd: 'load_data', dtname: 'customer', field: 'count(1) cnt', where: customerWhere, flag: 1 };
  var pCountParams = { cmd: 'load_data', dtname: 'product', field: 'count(1) cnt', where: productWhere, flag: 1 };

  var cData = await sendLoadData(cCountParams);
  var pData = await sendLoadData(pCountParams);
  var cCount = (cData.ok === 1 && cData.data[0]) ? parseInt(cData.data[0].cnt, 10) : 0;
  var pCount = (pData.ok === 1 && pData.data[0]) ? parseInt(pData.data[0].cnt, 10) : 0;

  // 如果增量数据量超过阈值，切换为全量分片获取
  if (cCount + pCount > INCREMENTAL_THRESHOLD) {
    log('增量数据量 ' + (cCount + pCount) + ' 条，超过阈值 ' + INCREMENTAL_THRESHOLD + '，切换为全量分片获取', 'info');
    await fetchFullDataBatched();
    return;
  }

  // 增量数据量在安全范围内，执行原有增量逻辑
  log('增量数据量 ' + (cCount + pCount) + ' 条，在安全范围内，执行增量获取', 'info');
  await fetchIncrementalData(); // 原有增量逻辑
}

7. OFFSET 性能注意事项

limit + start 本质是 MySQL 的 OFFSET ... LIMIT 分页。当 offset 值很大时，MySQL 需要扫描并跳过前面所有行，性能会退化：

OFFSET 值MySQL 行为性能影响
0 ~ 50,000扫描少量行后返回良好 几乎无影响
50,000 ~ 200,000需扫描并跳过大量行中等 查询耗时可能翻倍
200,000+扫描开销巨大较差 可能需要数秒
当前方案的适用范围：由于客户和产品各设置5万硬性上限，OFFSET 最大值为 50,000，性能完全可接受。如果未来需要提升上限，可考虑升级为基于ID范围的游标分页（WHERE id > lastMaxId LIMIT 20000），彻底避免 OFFSET 扫描问题。

  lastMaxId = Math.max.apply(null, list.map(function(item) { return parseInt(item.id, 10); }));
}

10. 总结
方案核心：利用 load_data 接口已有的 limit + start 分页能力，将一次全量读取拆分为多批次小量读取，每批读取后立即写入 IndexedDB 并生成拼音，批次间让出主线程避免 UI 冻结。
