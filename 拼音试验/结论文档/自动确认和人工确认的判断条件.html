自动确认与人工确认判断条件

产品匹配 · 客户匹配 · 同名区分 · 决策流程
创建：2026-05-17
实现：index.html / get_cus_pro.html
评分模型：四维加权（35%+25%+30%+10%）
自动确认阈值：≥90% / 唯一≥80%
1. 概述

拼音匹配完成后，系统需要决定匹配结果是自动确认还是人工确认。自动确认意味着系统认为匹配结果足够可靠，无需用户操作；人工确认意味着系统将结果标记为待定，需要用户审核。

核心原则：宁可多等一步，不可错配一条。自动确认的门槛设计偏保守——只有高置信度或唯一候选时才自动确认，其余一律交给人工。同名多产品必须通过型号/规格区分才能自动确认，否则必须人工选择。
2. 评分模型

匹配得分由四维加权计算得出（已移除未使用的业务权重维度）：

拼音相似度 × 35% + 首字母匹配 × 25% + 词袋余弦 × 30% + 长度匹配 × 10% = 最终得分
维度 权重 计算方式 作用
拼音相似度 35% 编辑距离 + LCS 取平均 核心匹配信号，全拼级别的字符串相似度
首字母匹配 25% 编辑距离 + LCS 取平均 短文本快速匹配，对缩写输入敏感
词袋余弦 30% 按 _ 分词后余弦相似度 解决词序不同问题，最稳健的维度
长度匹配 10% 1 - |lenA - lenB| / maxLen 防止短查询误匹配长记录
拼音生成一致性：查询端和数据库端使用相同的 generatePinyinForText 函数。产品拼音由品名+型号+规格合并生成，查询时也合并品名+型号传入，确保两端拼音空间一致。
占位符过滤（isPlaceholder）：合并生成拼音时，空值、"-"、"[未填写]"、"[空]" 等方括号占位符不参与合并。例如：model="[未填写]" 表示型号为空，不应生成拼音，否则无意义的占位文本会严重干扰匹配得分（曾导致100%匹配降至55%）。过滤逻辑统一使用 isPlaceholder() 函数：.filter(s => !isPlaceholder(s))，判断规则：!val || val.trim() === '-' || val.trim() === '[未填写]' || /^\[.*\]$/.test(val.trim())
3. 产品自动确认条件

产品匹配在以下5种情况下自动确认（status: 'confirmed'）：

≥90%
自动确认
条件1：高分唯一 · 品名匹配
得分≥90% 且同名产品只有1条 → 自动确认
matchType: 'exact'（≥95%）或 matchType: 'name'（90%-95%）
示例：输入"台式电脑"，数据库中只有1条"台式电脑"产品，得分95% → 自动确认
≥90%
自动确认
条件2：同名多产品 · 型号精确匹配
得分≥90% 且同名产品有多条，但输入的型号与某条产品型号完全一致 → 自动确认
matchType: 'sku'
示例：输入"视频会议 POLYCOM HDX 6000-720"，数据库有3条"视频会议"，其中1条型号为"POLYCOM HDX 6000-720" → 精确匹配该条
≥90%
自动确认
条件3：同名多产品 · 型号部分匹配
得分≥90% 且同名产品有多条，型号不完全一致但存在双向包含关系 → 自动确认
matchType: 'sku'
匹配规则：产品型号.indexOf(输入型号) !== -1 || 输入型号.indexOf(产品型号) !== -1
示例：输入型号"HDX 6000"，产品型号"POLYCOM HDX 6000-720"包含输入 → 部分匹配
≥90%
自动确认
条件4：同名多产品 · 规格匹配
得分≥90% 且同名产品有多条，型号不匹配但有规格值且规格包含匹配 → 自动确认
matchType: 'sku'
匹配规则：产品规格.indexOf(输入规格) !== -1
示例：输入规格"白色"，产品规格"3M白色防护服"包含"白色" → 规格匹配
≥80%
自动确认
条件5：唯一候选 · 高置信
匹配结果只有1条且得分≥80% → 自动确认
matchType: 'name'
设计理由：只有一个候选且分数较高时，用户确认的概率极高，自动确认减少操作步骤
示例：输入"15mm木塑"，只有1条匹配结果得分85% → 自动确认

6. 客户匹配条件

客户匹配与产品匹配使用相同的四维评分模型，但决策逻辑更简单——客户没有"同名多条+型号区分"的场景：

条件 状态 matchType 说明
得分≥90% confirmed exact 自动确认，调用 selectCustomer 回填客户信息
唯一候选 且 ≥80% confirmed exact 自动确认，减少操作步骤
得分70%-90% pending fuzzy 候选推荐，显示客户卡片待用户确认
得分45%-70% pending fuzzy 模糊匹配，需手动搜索或新建
得分<45% 或 无候选 error none 未匹配，需手动搜索或新建
客户与产品的关键差异
— 客户没有"同名多条+型号区分"逻辑，因为客户名称通常是唯一的
— 客户确认后自动调用 selectCustomer，回填标准客户名、地址、联系人
— 客户匹配的 matchType 只有 exact、fuzzy、none 三种，没有 sku
7. 同名产品区分策略

同名多产品是产品匹配中最复杂的场景。系统按以下优先级依次尝试区分：

型号精确匹配 → 型号部分匹配 → 规格匹配 → 人工选择
优先级 匹配方式 匹配规则 结果
1 型号精确匹配 产品型号 === 输入型号（不区分大小写） confirmed · sku
2 型号部分匹配 产品型号.indexOf(输入型号) ≥ 0 || 输入型号.indexOf(产品型号) ≥ 0 confirmed · sku
3 规格包含匹配 产品规格.indexOf(输入规格) ≥ 0 confirmed · sku
4 无法区分 以上均不满足 pending · name
为什么型号部分匹配也能自动确认？
ASR识别的型号可能不完整（如"HDX 6000" vs "POLYCOM HDX 6000-720"），双向包含匹配能覆盖这种局部匹配场景。但如果是完全无关的型号，不会触发包含匹配，仍会交给人工。
安全兜底：同名多产品且型号/规格都无法区分时，绝不自动确认。系统推荐第一条高分候选，但标记为 pending，必须由用户手动选择正确的型号。

9. UI状态映射

status 状态映射：

status 状态文本 边框颜色 操作按钮
confirmed 已确认 🟢 绿色 取消确认 · 重新匹配 · 删除
pending 待确认 🟡 黄色 确认 · 重新匹配 · 删除
error 未匹配 🔴 红色 新建产品 · 重新匹配 · 删除
new 新建 🟢 绿色 取消确认 · 重新匹配 · 删除

matchType 匹配类型映射：

matchType 显示文本 标签颜色 产生场景
exact 精确匹配 🟢 绿色底 品名匹配得分 ≥95%，同名唯一产品自动确认
sku SKU匹配 🔵 蓝色底 同名多产品，通过型号精确/部分匹配或规格匹配区分后确认
name 品名匹配 🟡 黄色底 品名匹配得分 90%-95%确认，或同名多条无法区分待确认，或候选推荐/模糊提示
code 编号匹配 🟢 绿色底 通过产品编号匹配确认
auto 自动匹配 🟢 绿色底 重新匹配窗口中得分 ≥90% 自动确认
candidate 候选推荐 🟡 黄色底 重新匹配窗口中得分 70%-90%
fuzzy 模糊匹配 🟠 橙色底 重新匹配窗口中得分 <70%，或客户匹配 45%-90%
none 未匹配 🔴 红色底 得分低于45%阈值，无匹配结果
new 新建产品 🔵 蓝色底 用户手动新建产品
注意：matchType 的所有可能值都必须在 UI 渲染的 matchTypeText 映射中定义，否则会回退显示为"待匹配"，导致已确认的产品仍显示错误的匹配类型标签。
