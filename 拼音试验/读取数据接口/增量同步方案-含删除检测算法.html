库存流水增量同步方案

含删除检测 — 分段二分查找算法 · 三层架构 · 效率优化

📋 一、问题背景与核心挑战

库存流水同步面临三重挑战：新增数据（入库、出库）需要拉取、更新数据（成本修改、数量变更）需要同步、删除数据需要检测并清理本地冗余记录。

其中删除数据的检测是最复杂的环节，因为系统存在两层删除机制：

  • 软删除（dflag=1）：记录保留在数据表中，可通过 dflag=1 AND modstm > lastSync 查询检测
  • 硬删除（DELETE）：记录从数据表中彻底消失，无任何痕迹，无法通过查询检测已不存在的 ID
核心矛盾：硬删除后，服务器上没有任何信息能告诉你"这条记录曾经存在且被删除了"。因此，纯时间戳方案无法检测硬删除，必须引入全量 ID 比对机制。

4.2 Step 1: 时间戳增量（新增+更新）

async function fetchIncrementalChanges(lastSyncTime) {
  // 新增 + 更新的记录
  const changed = await _sendRequest({
    cmd: 'load_data',
    dtname: 'libitem',
    field: 'id,type,lib,pid,nin,nout,num,date,sdate,cprice,status,creatstm,modstm,...',
    where: `dflag != 1 AND status = 1 AND (creatstm > '${lastSyncTime}' OR modstm > '${lastSyncTime}')`,
    flag: 1
  });

  // 软删除的记录（如果软删除时 modstm 有更新）
  const softDeleted = await _sendRequest({
    cmd: 'load_data',
    dtname: 'libitem',
    field: 'id',
    where: `dflag = 1 AND modstm > '${lastSyncTime}'`,
    flag: 1
  });

  return {
    changed: (changed.data || []).map(_mapFlowItem),
    softDeletedIds: (softDeleted.data || []).map(r => parseInt(r.id, 10))
  };
}

4.2.5 Step 1.5: 执行数据增量刷新（dtime 执行时间戳）

Step 1 基于 creatstm/modstm 捕获的是填单层的变更（新建、修改、软删除）。但在业务系统中，流水还有一层执行层的变更——审核通过、执行时间修改等，这些变更会更新 dtime（执行时间戳，Unix timestamp），但 不会更新 creatstm/modstm。

问题
仅靠 creatstm/modstm 增量查询，会遗漏执行层数据变更。
例如：一条流水昨天填单（creatstm=昨天），今天审核通过（dtime=今天的时间戳），
但 modstm 未更新 → Step 1 查不到 → 本地 dtime 仍为旧值 → 台账计算错误。

因此，在 Step 1 之后增加 Step 1.5，基于独立的 last_update_timestamp（Unix秒级时间戳），按 dtime 直接比对查询执行数据增量：

async function fetchExecutionChanges(lastUpdateTimestamp) {
  // dtime 是执行时间戳（Unix timestamp），直接用数值比对
  const whereCond = `dflag != 1 AND status = 1 AND dtime > ${lastUpdateTimestamp}`;

  const json = await _sendRequest({
    cmd: 'load_data',
    dtname: 'libitem',
    field: 'id,type,lib,pid,nin,nout,num,date,sdate,dtime,cprice,cost_money_rate,...',
    where: whereCond,
    flag: 1
  });

  return (json.data || []).map(_mapFlowItem);
}

双时间戳互补机制

场景 Step 1
creatstm/modstm		 Step 1.5
dtime
新建流水（填单）✅ creatstm 更新❌ dtime 可能为0
修改流水（改数量/成本）✅ modstm 更新❌ dtime 可能不变
审核通过（执行时间变更）❌ creatstm/modstm 可能不变✅ dtime 更新
执行时间被修改❌ creatstm/modstm 可能不变✅ dtime 更新
结论
creatstm/modstm 捕获填单层变更，dtime（执行时间戳）捕获执行层变更。两者互补，缺一不可。

last_sync_time 存储为字符串格式（'YYYY-MM-DD HH:mm:ss'），last_update_timestamp 存储为 Unix 秒级时间戳数值，两者在同步完成时分别写入。

4.2.6 写入语义：bulkPut = Upsert（覆盖写）

Step 1 和 Step 1.5 的增量数据都通过 syncBatchWriteTransactions 写入本地 IndexedDB，底层调用 Dexie.js 的 bulkPut 方法。其语义为 Upsert（存在则覆盖，不存在则插入）：

主键 ID 状态 bulkPut 行为 说明
本地不存在该 IDInsert — 插入新记录新增流水首次同步到本地
本地已存在该 ID覆盖写 — 用新数据整体替换旧记录已有流水的字段值被最新数据覆盖
注意
bulkPut 是整行覆盖，不是字段级合并。如果 API 返回的记录缺少某个字段（如 cprice 为空），覆盖后该字段也会变为空值。
当前 fetchIncrementalChanges 和 fetchExecutionChanges 均请求了完整的 field 列表，因此不存在字段丢失的风险。

这与 bulkAdd 不同——bulkAdd 遇到已存在的主键会抛出 ConstraintError，不适合增量同步场景。

4.2.7 Step 1 与 Step 1.5 的数据重叠处理

Step 1 按 creatstm/modstm 拉取增量，Step 1.5 按 dtime 拉取增量，两者可能返回相同 ID 的记录（一条流水既修改了填单信息又变更了执行时间）。由于都使用 bulkPut（Upsert 语义），重复写入不会产生数据错误，只是多做了一次覆盖写。

Step 3: 库存快照bulkPut（先清空再写）Insert不可能重复

4.3 Step 2: 分段二分删除检测 — 核心算法

这是整个方案的核心创新点。当第一层检测到差异后，进入删除检测阶段。传统方式是全量拉取 10 万个 ID 做比对。我们用分段二分查找将日常场景的 ID 传输量降低 80%+。

4.3.1 核心思想

洞察
10 万条数据中，真正被删除的 ID 通常只有几十~几百个（占比 <3%）

如果每 1 万条 ID 为一个段，则只有 1~3 个段包含删除
只需拉取这 1~3 个差异段的 ID，其余 7~9 个段直接跳过

4.3.4 算法伪代码

/**
 * 分段二分查找 — 检测本地多余记录（被硬删除的 ID）
 * @param {number} localMaxId - 本地最大 ID
 * @param {number} segmentSize - 每段大小，默认 10000
 * @param {number} threshold - 范围小于此值时切换为逐个比对，默认 100
 * @returns {Promise<number[]>} 被删除的 ID 列表
 */
async function detectDeletedIds(localMaxId, segmentSize = 10000, threshold = 100) {

  // ========== 第一步：分段 COUNT 粗定位 ==========
  const segmentCount = Math.ceil(localMaxId / segmentSize);
  const diffSegments = [];

  for (let seg = 0; seg < segmentCount; seg++) {
    const lo = seg * segmentSize + 1;
    const hi = Math.min((seg + 1) * segmentSize, localMaxId);

    // 服务器 COUNT（只返回 1 条记录，极轻量）
    const serverCount = await fetchSegmentCount(lo, hi);

    // 本地 COUNT
    const localCount = await syncDB.transactions
      .where('id').between(lo, hi, true, true).count();

    if (serverCount !== localCount) {
      diffSegments.push({ lo, hi, diff: localCount - serverCount });
    }
  }

  // ========== 第二步：根据差异段数 K 动态选择策略 ==========
  const K = diffSegments.length;
  const FULL_ID_API_COST = Math.ceil(localMaxId / 2000);  // 全量 ID 拉取的 API 次数
  const BINARY_API_COST = 10 + K * Math.ceil(Math.log2(segmentSize / threshold));  // 二分的预估 API 次数

  const deletedIds = [];

  if (K === 0) {
    // 无差异段，无需任何操作
    return [];
  } else if (BINARY_API_COST <= FULL_ID_API_COST) {
    // K 较小，二分更省 → 继续二分查找
    for (const seg of diffSegments) {
      const segDeleted = await binarySearchDelete(seg.lo, seg.hi, threshold);
      deletedIds.push(...segDeleted);
    }
  } else {
    // K 较大，二分反超 → 直接拉取差异段的全量 ID 做比对
    for (const seg of diffSegments) {
      const segDeleted = await segmentFullIdCompare(seg.lo, seg.hi);
      deletedIds.push(...segDeleted);
    }
  }

  return deletedIds;
}

/**
 * 差异段全量 ID 比对 — 当差异段数 K 较大时，直接拉取该段全部 ID 做比对
 * 比 binarySearchDelete 更适合删除量大的场景
 */
async function segmentFullIdCompare(lo, hi) {
  const serverIds = new Set(await fetchIdRange(lo, hi));
  const localIds = new Set(
    await syncDB.transactions
      .where('id').between(lo, hi, true, true)
      .primaryKeys()
  );
  const deleted = [];
  for (const id of localIds) {
    if (!serverIds.has(id)) deleted.push(id);
  }
  return deleted;
}

/**
 * 二分查找 — 在 [lo, hi] 范围内找出被删除的 ID
 */
async function binarySearchDelete(lo, hi, threshold) {
  if (lo > hi) return [];

  // 范围足够小时，切换为逐个比对策略
  if (hi - lo + 1 <= threshold) {
    return await bruteForceFindDeleted(lo, hi);
  }

  // 二分：取中点
  const mid = Math.floor((lo + hi) / 2);

  // 统计前半段的差异
  const frontServerCount = await fetchSegmentCount(lo, mid);
  const frontLocalCount = await syncDB.transactions
    .where('id').between(lo, mid, true, true).count();
  const frontDiff = frontLocalCount - frontServerCount;

  // 统计后半段的差异
  const backServerCount = await fetchSegmentCount(mid + 1, hi);
  const backLocalCount = await syncDB.transactions
    .where('id').between(mid + 1, hi, true, true).count();
  const backDiff = backLocalCount - backServerCount;

  // 递归处理差异段
  const results = [];
  if (frontDiff > 0) {
    results.push(...await binarySearchDelete(lo, mid, threshold));
  }
  if (backDiff > 0) {
    results.push(...await binarySearchDelete(mid + 1, hi, threshold));
  }

  return results;
}

/**
 * 逐个比对 — 范围足够小时，直接拉取并比对
 */
async function bruteForceFindDeleted(lo, hi) {
  // 拉取该范围内所有服务器 ID（只取 id 字段，flag=1，最快）
  const serverIds = await fetchIdRange(lo, hi);

  // 获取本地该范围所有 ID
  const localIds = new Set(
    await syncDB.transactions
      .where('id').between(lo, hi, true, true)
      .primaryKeys()
  );

  // 差集：本地有但服务器没有的 = 被删除的
  const deletedIds = [];
  for (const sid of serverIds) {
    localIds.delete(sid);
  }
  return [...localIds];
}

/**
 * 获取指定 ID 范围内的服务器记录数
 */
async function fetchSegmentCount(lo, hi) {
  const result = await _sendRequest({

4.3.5 完整第二层同步函数

async function doIncrementalSync(lastSyncTime) {
  const log = (msg, level) => appendLog(`[${now()}] ${msg}`, level);

  // ── Step 1: 时间戳增量（新增+更新） ──────────────────────────
  log('Step 1: 获取时间戳增量数据...', 'ok');
  const { changed, softDeletedIds } = await fetchIncrementalChanges(lastSyncTime);

  if (changed.length > 0) {
    await syncBatchWriteTransactions(changed);
    log(`写入 ${changed.length} 条新增/更新记录`, 'ok');
  }
  if (softDeletedIds.length > 0) {
    await syncDB.transactions.bulkDelete(softDeletedIds);
    log(`软删除 ${softDeletedIds.length} 条`, 'warn');
  }

  // ── Step 1.5: 执行数据增量刷新（dtime 执行时间戳） ──────────────
  log('Step 1.5: 刷新执行数据增量...', 'ok');
  const meta = await syncLoadSyncMeta();
  const lastUpdateTimestamp = meta?.last_update_timestamp || 0;

  if (lastUpdateTimestamp > 0) {
    const execChanged = await fetchExecutionChanges(lastUpdateTimestamp);
    if (execChanged.length > 0) {
      await syncBatchWriteTransactions(execChanged);
      log(`刷新 ${execChanged.length} 条执行数据变更记录`, 'ok');
    } else {
      log('无执行数据变更', 'ok');
    }
  } else {
    log('首次同步，跳过执行数据增量刷新', 'ok');
  }

  // ── Step 2: 分段二分删除检测（硬删除） ────────────────────────
  log('Step 2: 检测硬删除记录...', 'ok');
  const localMaxId = (await syncDB.transactions.orderBy('id').last())?.id || 0;
  const deletedIds = await detectDeletedIds(localMaxId, 10000, 100);

  if (deletedIds.length > 0) {
    await syncDB.transactions.bulkDelete(deletedIds);
    log(`硬删除 ${deletedIds.length} 条记录`, 'warn');
  } else {
    log('未检测到硬删除记录', 'ok');
  }

  // ── Step 3: 库存快照 ─────────────────────────────────────────
  log('Step 3: 同步库存快照...', 'ok');
  const invData = await fetchInventorySnapshot();
  await syncClearInventory();
  await syncBatchWriteInventory(invData);
  log(`库存快照同步完成：${invData.length} 条`, 'ok');

  // ── Step 4: 更新同步元信息 ───────────────────────────────────
  const serverTime = await getServerTime();  // 取服务器时间，避免时钟偏移
  await syncSaveSyncMeta({
    last_sync_time: serverTime,
    last_sync_mode: 'incremental',
    last_update_timestamp: serverTimestamp  // Unix秒级时间戳，用于 Step 1.5 dtime 比对
  });

  return {
    changedCount: changed.length,
    deletedCount: deletedIds.length + softDeletedIds.length,
    invCount: invData.length
  };
}

5.3 全量校准流程

/**
 * 第三层：全量校准
 * - 清空本地 transactions 表
 * - 分页拉取服务器全部数据
 * - 写入本地 IndexedDB
 * - 更新同步元信息
 */
async function doFullCalibration() {
  appendLog('全量校准：清空本地流水数据...', 'warn');
  await syncClearTransactions();
  await syncClearCheckpoint();

  // 获取总记录数
  const totalCount = await fetchTotalCount('libitem', 'dflag != 1 AND status = 1');
  appendLog(`全量校准：待拉取 ${totalCount} 条记录`, 'ok');

  // 分页拉取
  const pageSize = 2000;
  let start = 0;
  let synced = 0;

  while (true) {
    const { items, hasMore } = await fetchFlowPage(start, pageSize);
    if (items.length === 0) break;

    await syncBatchWriteTransactions(items);
    synced += items.length;
    start += items.length;

    // 进度回调
    onProgress({
      total: totalCount,
      done: synced,
      progress: (synced / totalCount * 100).toFixed(1)
    });

    if (!hasMore) break;
    await sleep(300);  // 限流
  }

  // 更新元信息
  await syncSaveSyncMeta({
    last_sync_time: await getServerTime(),
    last_sync_mode: 'full',
    last_calibration_time: new Date().toISOString()
  });

  return { totalCount: synced };
}

🎯 六、完整同步入口函数

/**
 * 完整同步流程入口
 * 由 UI 按钮触发
 *
 * @param {'auto'|'incremental'|'full'} mode
 *   - 'auto': 自动选择（默认）
 *   - 'incremental': 强制走第二层增量
 *   - 'full': 强制全量校准
 */
async function startSync(mode = 'auto') {
  // ── 预检查 ────────────────────────────────────────────────────
  if (!syncDexieReady) {
    showToast('同步功能不可用（Dexie.js 未加载）', 'error');
    return;
  }

  // ── 自动模式：预检 ────────────────────────────────────────────
  if (mode === 'auto') {
    const diffResult = await quickDiffCheck();

    // 差异过大，直接建议全量
    const diffRatio = diffResult.countMatch ? 0 : Math.abs(diffResult.serverCount - diffResult.localCount)
      / Math.max(diffResult.serverCount, diffResult.localCount);

    if (diffRatio > 0.15) {
      const confirmed = await showConfirmModal('数据差异较大（' + (diffRatio * 100).toFixed(1) + '%），' +
        '建议执行全量同步以确保数据完整。是否继续？');
      if (confirmed) {
        return await doFullCalibration();
      } else {
        return;
      }
    }

    // 无差异，跳过同步
    if (diffResult.countMatch && diffResult.maxIdMatch) {
      showToast('数据已是最新，无需同步', 'success');
      return;
    }
  }

  // ── 执行同步 ──────────────────────────────────────────────────
  if (mode === 'full') {
    return await doFullCalibration();
  }

  // 'auto' 或 'incremental' 模式：走第二层
  const lastSyncTime = (await syncLoadSyncMeta())?.last_sync_time || '1970-01-01 00:00:00';
  return await doIncrementalSync(lastSyncTime);
}

/**
 * 快速差异检查（第一层）
 * @returns {Promise<{countMatch, maxIdMatch, serverCount, localCount, serverMaxId, localMaxId}>}
 */
async function quickDiffCheck() {
  const [serverCount, localCount, serverMaxId, localMaxId] = await Promise.all([
    fetchTotalCount('libitem', 'dflag != 1 AND status = 1'),
    syncDB.transactions.count(),
    fetchMaxId(),
    syncDB.transactions.orderBy('id').last().then(r => r?.id || 0)
  ]);

  return {
    countMatch: serverCount === localCount,
    maxIdMatch: serverMaxId === localMaxId,
    serverCount, localCount, serverMaxId, localMaxId
  };
}

7.3 效率边界分析：删除越少，节省越多

分段二分算法的核心特性：删除数据越少，比全量 ID 对比节约的时间越多。这是单调递增关系，下面严格证明。

7.3.1 全量 ID 对比的固定成本

不管删除多少条，全量 ID 方案的代价是恒定的：

全量 ID 10万条 ID，分页 2000条/页 → 50 次 API → 传输 800KB → 约 15s
无论删除 0 条还是 5000 条，这 15 秒都要花。

7.3.2 分段二分的可变成本

阶段成本与删除量的关系
分段 COUNT 粗定位10 次 API（固定）无关 — 无论删多少，都要扫 10 段
二分查找精定位每差异段 log₂(段大小/阈值) 次 API正相关 — 删除越少，差异段越少，二分越少

关键：删除越少 → 差异段越少 → 二分越少 → 总成本越低。

7.3.3 量化对比

假设 10 万条数据，分 10 段（每段 1 万），二分阈值 100：

删除量差异段数 K分段COUNT二分API总API全量ID方案节省
0 条0 段10 次0 次10 次50 次80%
5 条（集中1段）1 段10 次~7 次17 次50 次66%
20 条（分散2段）2 段10 次~14 次24 次50 次52%
100 条（分散4段）4 段10 次~28 次38 次50 次24%
500 条（分散8段）8 段10 次~56 次66 次50 次❌ 反超 32%
3000 条（全段差异）10 段10 次~70 次80 次50 次❌ 反超 60%

7.3.4 反转点公式

设 N = 总ID数, S = 段大小, T = 二分阈值, K = 差异段数

全量 ID API = ceil(N / 2000) = 50 次（固定）
分段二分 API = ceil(N/S) + K × log₂(S/T) = 10 + 7K

反转条件 10 + 7K > 50 → K > 5.7 → K ≥ 6 段时反转

结论 删除数据越少，差异段 K 越小，节省越多。单调递减关系。
当 K ≥ 6（约 200+ 条删除且分散）时，方案反转，全量更优。

7.4 动态切换策略：永远不比全量更差

基于上述反转点分析，在分段 COUNT 粗定位完成后，根据实际差异段数 K 动态决定后续策略：

┌───────────────────────────────────────────────────────────────────────────┐ │ 动态切换策略 — 分段 COUNT 完成后自动选择最优路径 │ ├───────────────────────────────────────────────────────────────────────────┤ │ │ │ 分段 COUNT 粗定位完成 → 发现 K 个差异段 │ │ │ │ ┌──────────────────────────────────────────────┐ │ │ │ │ │ │ K ≤ 5 段 K > 5 段 │ │ │ │ │ │ ▼ ▼ │ │ ┌──────────────────┐ ┌──────────────────────────┐ │ │ │ 继续二分查找 │ │ 直接拉取 K 个差异段的全量 │ │ │ │ (更省，10+7K 次) │ │ ID 做比对 │ │ │ │ │ │ (K段 × 5页/段 = 5K 次) │ │ │ │ 例：K=2 → 24次 │ │ 例：K=8 → 40次 │ │ │ │ 全量需50次，省52% │ │ 全量需50次，省20% │ │ │ └──────────────────┘ └──────────────────────────┘ │ │ │ │ 保证：无论 K 多大，本方案 API 次数 ≤ 全量 ID 方案（50 次） │ │ │ │ 极端情况 K=10（全段差异）：直接走全量 ID 拉取（50次），不二分（80次） │ │ │ └───────────────────────────────────────────────────────────────────────────┘
核心保证：动态切换策略确保算法永远不会比全量 ID 方案更差。删除少时大幅节省，删除多时自动退化为全量拉取差异段，最坏情况等价于全量方案。
算法复杂度：分段二分查找的 API 调用次数 = O(log₂(N)) + O(m×log₂(S))，其中 N=总ID数，S=段大小，m=差异段数。日常场景（m=1~3，删除<50条）下，总调用约 10+15 = 25 次，相比全量同步 50 次，节省 50% 的 API 调用。

⚠️ 八、前置条件与依赖

8.1 MySQL 索引要求

-- 必须在 libitem 表上创建以下索引，否则增量查询会走全表扫描

-- 1. 增量查询核心索引（creatstm + modstm，覆盖时间戳范围查询）

ALTER TABLE libitem ADD INDEX idx_dflag_modstm (dflag, modstm);

8.2 modstm 可靠性验证

需要确认数据库软删除操作是否会更新 modstm 字段。可通过以下 SQL 在测试环境验证：

-- 在测试环境执行一条记录软删除后，检查 modstm 是否更新
SELECT id, dflag, creatstm, modstm
FROM libitem
WHERE dflag = 1
ORDER BY modstm DESC
LIMIT 10;

-- 验证：所有 dflag=1 的记录，modstm 是否 > creatstm
-- 如果 modstm 为空或等于 creatstm，说明软删除时 modstm 未更新
-- 此时软删除检测方案退化为仅依赖硬删除的 ID 比对

8.3 creatstm/modstm 格式确认

确认 creatstm 和 modstm 的数据格式，影响 WHERE 条件写法：

  • 如果是 YYYY-MM-DD HH:mm:ss 格式：直接字符串比较即可
  • 如果是 Unix 时间戳（整数）：需要用 UNIX_TIMESTAMP() 转换
  • 如果是毫秒级时间戳：需要除以 1000 后比较
重要：建议在 API 层统一将 last_sync_time 格式化为与服务器 creatstm/modstm 一致的格式，避免格式不匹配导致的查询错误。
