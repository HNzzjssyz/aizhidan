# str_ps 格式细节（实测，必看）

## 关键发现：分隔符不是普通空格

`str_ps` 字段中**多个策略之间的分隔符是 `&nbsp;`（U+00A0 不间断空格）**，不是文档示例里看上去的普通空格。直接用 `split(' ')` 或 `split(/\s+/)` 得不到多条记录，会把整串当作一段。

实测样例（数据库原始值）：
```
VIP客户价:1990.00&nbsp;零售价:19988.00&nbsp;普通会员价格:19955.00
```

肉眼看到像是空格，但实际每个分隔符的字符编码是 `U+00A0`：
| 字符 | Unicode | 含义 |
|---|---|---|
| ` ` | U+0020 | 普通空格（`split(' ')` 切的是这个） |
| `&nbsp;` / ` ` | U+00A0 | 不间断空格（**str_ps 实际用的这个**） |
| `　` | U+3000 | 全角空格（少数情况下出现） |

## 兼容解析代码（JavaScript）

```javascript
function _parseStrPs(strPs) {
  var dict = {};
  if (!strPs || typeof strPs !== 'string') return dict;

  // 1) 先把多种"空格"还原为普通空格 U+0020
  var normalized = strPs
    .replace(/&nbsp;/gi, ' ')     // HTML 实体 nbsp（数据库存储时可能已转义）
    .replace(/&amp;nbsp;/gi, ' ') // 双层转义
    .replace(/\u3000/g, ' ')      // 全角空格
    .replace(/\u00A0/g, ' ');     // 不间断空格（str_ps 真实分隔符）

  // 2) 用空白字符分割
  var parts = normalized.trim().split(/\s+/);

  // 3) 每段按 "类型:价格" 解析（冒号支持半角/全角）
  for (var i = 0; i < parts.length; i++) {
    var p = parts[i];
    if (!p) continue;
    var idx = p.search(/[:：]/);
    if (idx <= 0) continue;
    var typeName = p.substring(0, idx).trim();
    var priceStr = p.substring(idx + 1).trim();
    var price = parseFloat(priceStr.replace(/[^0-9.\-]/g, ''));
    if (typeName && price > 0) dict[typeName] = price;
  }
  return dict;
}

// 用法
var d = _parseStrPs("VIP客户价:1990.00&nbsp;零售价:19988.00&nbsp;普通会员价格:19955.00");
// → { 'VIP客户价': 1990, '零售价': 19988, '普通会员价格': 19955 }
```

## 容易踩的坑

| 现象 | 根因 |
|---|---|
| 解析后只得到 1 条策略 | `split(' ')` / `split(/\s+/)` 切不动 `&nbsp;`，整串被当作一段 |
| 聚合"策略类型"时把所有产品的 str_ps 串连成一长串显示在 chip 上 | 解析失败 → typeName 是整串 → 看起来像是"很多策略挤在一起" |
| `dict[选中的策略名]` 永远是 undefined，回填价格为 0 | 上一条的后续：选中的策略名对不上整串 key |
| 截图里 chip 显示 `零售价:1998&普通会员价格:1995&VIP客户价 ¥1990.00` | 同一根因：typeName 拼成了整条 str_ps |

## 调试建议

在浏览器 Console 直接验证：
```javascript
// 复制一个 str_ps 实测值
var s = "VIP客户价:1990.00\u00A0零售价:19988.00\u00A0普通会员价格:19955.00";

```

## 适用范围

只要数据库里 `str_ps` 字段是按"客户类型:价格"成对、用空白字符分隔的，都应使用上面这份兼容解析。`price` 和 `buy_price` 字段是普通字符串数字，不涉及此问题。



# 前端使用：选择产品弹窗的价格显示（v1.4 起）

> 适用版本：pinyin_sync.js + pinyin_match.js + index.html（2026-06-10 升级）

## 1. 数据流

```
后端 product 表
   ↓ [load_data field 含 price]
pinyin_sync.js 拉取
   ↓ [组装 allProducts/productModified 时 price: item.price || '']
IndexedDB product 表（每条记录都有 price 字段）
   ↓ [getProductMapCached() / getProductNameIndexCached()]
前端 fuzzyMatch 候选对象 .price
   ↓ [渲染时「参考价：¥xx.xx」]
"选择产品"弹窗候选列表
```

## 2. 后端字段（同步层）

`pinyin_sync.js`：

| 同步类型 | field 列表 |
|---------|------------|
| 增量 | `id,pro_name,model,spec,price,modstm` |
| 全量 | `id,pro_name,model,spec,price` |

组装时显式带 `price`：
```javascript
productModified.push({
  id: item.id, name: item.pro_name || item.name || '',
  model: item.model || '', spec: item.spec || '', price: item.price || '',
  modstm: item.modstm
});
```

## 3. 拼音缓存（写入层）

`pinyin_sync.js` §拼音生成：

- **跳过判断**纳入 price 字段：原 `name/model/spec` 三字段比较，增加 `existing.price === (p.price || '')`
- **缓存写回**：`pp[key] = { id, name, model, spec, price: p.price || '', pinyin, pinyin_abbr }`

效果：价格变化会触发重新生成拼音（合理，因为价格变了说明产品信息有变更，拼音索引需要重建）。

## 4. 匹配层（pinyin_match.js）

匹配命中后构造 `matchedProduct` 时显式带 price：
- L1192 specMatch：`price: specMatch.price || ''`
- L1199 cp：`price: cp.price || ''`
- L1351 mp：`price: mp.price || ''`

results 数组增加 `matchedPrice: matchedProduct ? matchedProduct.price : ''`，前端可直接取用。

## 5. 前端选择产品弹窗（index.html）

### 5.1 三个 fuzzyMatch 函数透传 price

`fuzzyMatchByPinyin` / `fuzzyMatchByKeyword` / `fuzzyMatchByMixed` 三个函数：
- 函数开头：`var productMap = await getLSProductMap();`
- 每个 `.map()` 内：`var fullP = productMap[String(p.id)] || p;` → 返回对象加 `price: fullP.price || ''`

按 id 从 `getLSProductMap()` 查全量 product（含 price），回退到原 p（保底）。

### 5.2 渲染：候选列表加价格行

```html
<div class="candidate-item" onclick="selectProductForEdit('...')">
  <img class="candidate-img" ...>
  <div class="candidate-rank">1</div>
  <div class="candidate-info">
    <div class="candidate-name">金士顿 Micro SD卡(16G) Micro5</div>
    <div class="candidate-meta">PRD-4 | SKU: Micro5 候选推荐</div>
    <div class="candidate-price" style="font-size:12px;margin-top:2px;">
      参考价：<span style="color:#ef4444;font-weight:600;">¥75.69</span>
    </div>
  </div>
  <div class="candidate-similarity">89%</div>
</div>
```

样式说明：
- 有价格：红色加粗显示
- 无价格：灰色显示"待询价"

### 5.3 confirmProduct 流程透传

`selectProductForEdit` / `fillProductStandardData` 构造 matchedProduct 时带 `price: p.price || ''`，并把 `currentProducts[i].matchedPrice` 赋值为 `matchedProduct.price`。

订单"单价"列渲染：`product.price || '待询价'`（已能正确展示）。

## 7. 常见问题

| 现象 | 根因 | 修复 |
|------|------|------|
| 选择产品弹窗候选不显示价格行 | 旧版未升级 | 跑 `python3 _build_split.py` 同步 dev/ + prod/ |
| 价格行显示"待询价"但实际有价格 | IndexedDB 中 product 没 price 字段（同步时间在升级前） | 重新执行一次全量同步 |
| 候选价格不准 | price 字段没有保留原始格式（被转成 number） | 同步组装时用 `item.price || ''` 保留原值 |
| 拼音生成频繁（性能下降） | 跳过判断未纳入 price，价格变化导致每次都重生成 | 确认 pinyin_sync.js L356 包含 `existing.price === (p.price || '')` |



# 读取当前客户当前产品的历史成交价格 

## 方法：通过loaddata接口实现
- cmd:load_data
- dtname:所属数据表
- field: 要读取的字段。多个用逗号分隔。如果不指定，默认读取列表中的所有字段。
- where: 读取条件。如果不指定，默认读取所有数据。
- order: 排序字段。如果不指定，默认不排序。
- limit: 读取条数。如果不指定，默认读取10条数据。
- start: 读取起始位置。如果不指定，默认从0开始。
- flag: flag=1指向数据表信息读取。如果不指定，默认指向字段函数级别的读取

## 示例：
- 请求例子（GET 形式，queryString 拼接）：
    /system/api.xt?cmd=load_data&dtname=goods&where=name=125%20and%20cu_id=5754&order=id%20desc&limit=1&field=id,un_price,micro_zk,sum

- Json方式（POST 形式，推荐使用，规避 where/order 里的空格/中文编码问题）：
```javascript
fetch('/system/api.xt', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({
    cmd: 'load_data',
    dtname: 'goods',
    field: 'id,un_price,micro_zk,sum',
    where: 'name=125 and cu_id=5754',
    order: 'id desc',
    limit: 1
  })
}).then(res => res.json()).then(data => console.log(data));
```
    - 等价于上面 GET 请求例子
    - where / order / limit / field 全部由后端 `JSON.parse` 解析，不再走 queryString 拼接/编码
    - 含空格或中文的 where 条件（如 `cu_id=梦蝶北京`）建议用此方式，避免 `encodeURIComponent` 漏写或重复转义
- 说明：
    - dtname：goods（交付计划/订单明细表）
    - where：name=125 and cu_id=5754 （name产品ID，cu_id客户ID）
    - order：id desc （按ID降序排序）
    - limit：1 （只读取一条数据）
    - field：id,un_price （读取ID和单价字段）
    - 注意：这里没有flag参数，所以是从字段函数级别读取数据
- 返回值例子：
```json
{"ok":1,"msg":"读取成功","data":[{"id":"875","un_price":"2000","micro_zk":"-RMB40.00(98%)","sum":"1960"}],"info":{"table":"goods","tablename":"交付计划\/订单明细","fields":{"id":"ID","un_price":"单价","micro_zk":"折扣","sum":"金额"}}}
```
- 返回值说明：
    - 其中 data：[{"id":"875","un_price":"2000","micro_zk":"-RMB40.00(98%)","sum":"1960"}] 是数据返回值
    - 下方是字段和中文字段名的对应关系
- **【重要】响应字段语义**（与请求 where 看上去的语义不同）：
    - `id`：记录主键（自增 ID，与产品无关，**不是**产品 ID）
    - `name`：**完整规格名**（如"金士顿CF(8G)/CF8G[个]"），含基础名 + "/" + SKU + "[单位]"
        - 例如：基础产品名"金士顿CF(8G)" + SKU"CF8G" + 单位"[个]" → 响应 `name`="金士顿CF(8G)/CF8G[个]"
        - 例如：基础产品名"爱国者迷你王 商务型L8202(16G)" + SKU"IP23" + 单位"[套]" → 响应 `name`="爱国者迷你王 商务型L8202(16G)/IP23[套]"
        - 虽然请求 where 里写的是 `name=125`（产品 ID 也能匹配），但响应里 name 字段返回的是**人类可读的产品名称**
    - `cu_id`：**客户名称**（如"〖飞奥德〗"），**不是**数字客户 ID
    - 所以前端拿到响应后要做产品匹配，**推荐"去单位后精确匹配"**：
        1. 把响应 `name` 末尾的 `[单位]` 剥掉（正则：`/[\[【（(][^)\]】]*[\]】）)]\s*$/`）
        2. 与"我们的完整产品名（品名 + "/" + SKU）"做精确相等
        3. 兜底：双向前缀匹配（兼容历史数据）
