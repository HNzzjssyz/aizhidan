选型决策推演

原方案：双技术栈

  • 前端：阿里云ASR（WebSocket推流）
  • 后端：扣子智能体（LLM提取+结构化）
  • 热词是阿里云ASR唯一的差异化优势
  • SaaS多租户场景下热词配额限制（500/表，5000总计）不可用
  • 热词优势失效后，阿里云ASR与扣子ASR质量差异不大

新方案：扣子全栈

  • ASR：扣子语音插件（内置，零集成）
  • LLM：扣子智能体（内置，数据流闭环）
  • 无需跨平台传文本，全链路在扣子内完成
  • 一个技术栈 > 两个技术栈：更少代码、更少故障点
  • 拼音索引匹配兜底同音字问题，不依赖ASR层热词

核心决策逻辑

不用热词 → 阿里云ASR无差异化优势 → 后端已用扣子智能体 → 统一用扣子更合理 → 一个技术栈比两个好。拼音索引匹配是通用SaaS场景下热词问题的核心兜底机制，与ASR选型无关。

核心创新：拼音输出策略

让智能体输出拼音而非汉字，从源头绕开ASR同音字问题——这是本方案最关键的创新点。

核心洞察

ASR将语音转为文字时，同音字是最常见的错误类型——"华创科技"可能被识别为"华闯科技"。但同音字的拼音完全相同，如果智能体输出拼音而非汉字，同音字错误在拼音层被自然消除。

01

传统方案 vs 拼音输出方案

传统方案：输出汉字

  • ASR输出："深圳华闯科技要A3打印纸"
  • LLM提取：customer="深圳华闯科技"
  • 数据库查询：WHERE name = "深圳华闯科技"
  • 结果：匹配失败（"闯" ≠ "创"）
  • 需额外纠错逻辑，复杂且不可靠

新方案：输出拼音

  • ASR输出："深圳华闯科技要A3打印纸"
  • LLM提取+转拼音：customer_pinyin="shen_zhen_hua_chuang_ke_ji"
  • 数据库查询：WHERE pinyin = "shen_zhen_hua_chuang_ke_ji"
  • 结果：匹配成功
  • 同音字在拼音层自然消除，无需纠错
02

为什么拼音输出能绕开同音字

ASR错误类型 ASR输出示例 拼音输出 能否匹配
同音字替换 华闯科技 hua_chuang_ke_ji 与"华创科技"拼音一致
近音字替换 华创科捷 hua_chuang_ke_jie 编辑距离容错
声调差异 华闯(huá chuǎng) hua_chuang 无声调拼音无差异
多音字 重庆重钢 chong_qing_chong_gang / zhong_gang 需全读音展开
中英混排 A3打印纸 A3_da_yin_zhi 英文保留原字符
音节增删 深圳华创科 shen_zhen_hua_chuang_ke 编辑距离容错

关键结论

ASR最常见的错误类型是同音字替换，占错误总量的60-70%。拼音输出策略将这类错误的影响降为零。剩余的近音字、音节增删等错误，通过编辑距离和LCS算法在拼音匹配层容错。两层防线叠加，理论匹配率可达90%以上。

03

拼音格式规范：下划线分词

格式定义

  • 规则：每个汉字的拼音之间用下划线 _ 分隔
  • 英文/数字：保留原字符，与相邻拼音之间也用下划线分隔
  • 无声调：拼音不带声调标记
  • 全小写：拼音字母全部小写（英文品牌名除外）

示例

  • "深圳华创科技" → shen_zhen_hua_chuang_ke_ji
  • "A3打印纸" → A3_da_yin_zhi
  • "B5笔记本" → B5_bi_ji_ben
  • "无线鼠标" → wu_xian_shu_biao
  • "重庆重钢" → chong_qing_zhong_gang
对比维度无分隔符（旧）下划线分词（新）
可读性wuxianshubiao（难辨词边界）wu_xian_shu_biao（清晰分词）
部分匹配wuxian 可能匹配"无线"或"五县"wu_xian 精确匹配"无线"
前缀索引前N字符可能切断词边界按词切分，前缀索引更精确
编辑距离字符级偏移导致连锁错误词级偏移，错误隔离在单词内
数据库查询WHERE pinyin_full = 'wuxianshubiao'WHERE pinyin_full = 'wu_xian_shu_biao'

一致性要求

智能体输出拼音和数据库拼音索引必须使用相同的格式规范。只要两端格式一致，匹配就不会出错。下划线分词格式是全链路统一标准，从智能体Prompt到数据库建表到后端匹配算法，全部遵循此格式。

扣子平台内闭环

扣子平台负责

  • 语音识别：扣子语音插件（ASR）
  • 结构化提取：扣子智能体（LLM）
  • 拼音转换：扣子智能体（LLM内置能力）
  • JSON输出：扣子Workflow结构化输出

后端服务负责

  • 拼音索引查询：客户表/产品表 pinyin 字段

  • 匹配结果返回：候选列表 + 置信度
  • 单据生成：格式化单据草稿

为什么LLM能做拼音转换

大语言模型（如豆包）具备完整的中文拼音知识，能准确将汉字转为拼音，包括处理多音字（根据上下文判断读音）和中英混排（保留英文原字符）。这是LLM的内置能力，无需额外接入拼音库。且LLM转换拼音时，即使输入文本含同音字错误，输出的拼音仍然正确——因为同音字的拼音相同。

扣子智能体设计

智能体的核心职责：从ASR文本中提取客户名和产品名，并输出拼音。Prompt设计是关键。

01

智能体Prompt设计

## 角色 你是一个智能制单助手，负责从语音识别文本中提取结构化业务信息。 你的输出将被后端系统自动解析，因此必须严格遵循指定的JSON格式。 ## 核心任务 从语音识别文本中提取两类关键信息： 1. 客户名称 — 识别文本中的客户/公司名称 2. 产品明细 — 识别每个产品的名称、数量、单价、折扣、备注 ## 拼音转换规则（最关键） 客户名称和产品名称必须同时输出拼音，规则如下： - 将中文字符转换为无声调拼音，英文和数字保留原字符 - 示例："深圳华创科技" → "shen_zhen_hua_chuang_ke_ji" - 示例："A3打印纸" → "A3_da_yin_zhi" - 示例："B5笔记本" → "B5_bi_ji_ben" - 多音字按上下文判断最可能读音作为主拼音，其他可能读音放入alternatives数组 - 拼音按下划线分词格式输出，每个汉字的拼音之间用下划线 _ 分隔，如"深圳华创科技" → "shen_zhen_hua_chuang_ke_ji" ## 关键设计决策：为什么让LLM做拼音转换而非后端

方案A（LLM转换）：智能体直接输出拼音，后端只需做索引查询。优点：LLM理解上下文可处理多音字，减少后端依赖；数据流更简洁。
方案B（后端转换）：智能体输出汉字，后端用pypinyin库转拼音。优点：拼音转换更精确可控；缺点：多一次转换环节，且汉字若含ASR错误，pypinyin可能按错误字读音转换。

选择方案A：LLM做拼音转换时，即使输入含同音字错误（如"华闯"），LLM理解上下文后仍会输出正确拼音"hua_chuang"。而pypinyin会按"闯"字读音转换，结果也是"hua_chuang"——两者等价，但LLM方案少一个环节。

05

拼音索引匹配算法

智能体输出拼音后，后端通过拼音索引查询+相似度算法完成客户/产品的精准匹配。

01

数据库拼音索引设计

-- 客户表拼音索引 CREATE TABLE customer_pinyin_index ( id BIGINT PRIMARY KEY, customer_id BIGINT NOT NULL, customer_name VARCHAR(200) NOT NULL, pinyin_full VARCHAR(500) NOT NULL, -- 全拼：shen_zhen_hua_chuang_ke_ji pinyin_prefix VARCHAR(100) NOT NULL, -- 前缀：shenzhenhua (前3字) pinyin_initials VARCHAR(100) NOT NULL, -- 首字母：szhckj length INT NOT NULL, -- 拼音长度 INDEX idx_prefix (pinyin_prefix), INDEX idx_initials (pinyin_initials), INDEX idx_length (length) ); -- 产品表拼音索引 CREATE TABLE product_pinyin_index ( id BIGINT PRIMARY KEY, product_id BIGINT NOT NULL, product_name VARCHAR(200) NOT NULL, pinyin_full VARCHAR(500) NOT NULL, -- 全拼：A3_da_yin_zhi pinyin_prefix VARCHAR(100) NOT NULL, pinyin_initials VARCHAR(100) NOT NULL, spec_pinyin VARCHAR(300), -- 规格拼音 category VARCHAR(50), -- 产品分类 length INT NOT NULL, INDEX idx_prefix (pinyin_prefix), INDEX idx_initials (pinyin_initials), INDEX idx_category (category) );
02

三级匹配策略

第一级：精确匹配

  • WHERE pinyin_full = 输入拼音
  • 命中率：约60-70%
  • 同音字场景全部命中
  • 直接自动确认，无需人工

第二级：前缀+长度过滤

  • WHERE pinyin_prefix = 输入前3字拼音 AND |length差| < 30%
  • 缩小候选集到5-50条
  • 对候选集计算编辑距离+LCS
  • 按相似度排序，取Top3

第三级：首字母+模糊匹配

  • ▸WHERE pinyin_initials = 输入首字母（如 szhckj）
  • ▸候选集可能较大（50-200条），需结合业务权重排序
  • ▸弹出候选列表，人工选择确认
03

相似度评分算法

维度 算法 权重 说明
全拼相似度 Levenshtein编辑距离 40% 容忍1-2个音节的增删替换
首字母匹配度 LCS最长公共子序列 25% "华创科技"匹配"华创科技有限公司"
长度相似度 1 - |len差|/max(len) 15% 过滤长度差异过大的候选
业务权重 历史交易频次+金额 20% 高频客户/产品优先
score = 0.40 × pinyin_sim + 0.25 × initial_sim + 0.15 × length_sim + 0.20 × business_weight
≥90% → 自动确认  |  70%-90% → 候选列表  |  <70% → 模糊提示

同音字的拼音相同，这是汉语拼音系统的基本特性。ASR最常见的错误类型（同音字替换，占60-70%）在拼音层被完全消除。剩余错误类型（近音字、音节增删）通过编辑距离容错。

验证通过

技术可行性

扣子语音插件支持中文ASR；扣子智能体（豆包LLM）具备完整的中文拼音知识，能准确转换拼音和处理多音字；后端拼音索引查询是成熟的数据库技术。

验证通过

工程可行性

扣子全栈零跨平台集成，MVP可在1-2周内完成。拼音索引建表是标准SQL操作，匹配算法（编辑距离、LCS）有成熟实现。无需对接第三方ASR服务。

验证通过

风险与应对

识别关键风险点，制定应对策略，确保方案稳健落地。

高风险

扣子ASR中文识别质量未经验证

方案定性描述"中文质量好"，但未建立量化基线。如果基础CER过高，拼音输出策略也无法补救。

应对：MVP第一周用标准测试集实测扣子ASR的CER，建立质量基线。若CER >15%，启动阿里云ASR备选方案。
中风险

LLM拼音转换准确性

LLM转换拼音可能出错，尤其是生僻字、多音字、行业术语。错误拼音会导致匹配失败。

应对：后端用pypinyin库做二次校验，当LLM输出拼音与pypinyin结果不一致时，两个拼音都做匹配查询。保留original字段供人工核对。
中风险

扣子平台锁定风险

全栈依赖扣子平台，如果平台涨价、限流或停止服务，迁移成本高。

应对：架构设计时将"ASR层"和"LLM层"抽象为可替换接口。扣子ASR和智能体可通过API Gateway替换为阿里云ASR + 自建LLM，拼音匹配层无需改动。
低风险

扣子智能体延迟

扣子智能体的响应延迟可能较高，影响用户体验。

应对：实测端到端延迟。扣子ASR+LLM内部链路可能比跨平台方案更快（少一跳网络传输）。若延迟超标，优化Prompt长度和输出格式。
