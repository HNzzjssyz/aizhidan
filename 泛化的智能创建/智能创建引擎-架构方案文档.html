01

背景与目标

当前已落地智能制单功能，核心边界为基于客户和产品信息识别生成销售订单。该功能验证了"自然语言输入 → 智能体识别 → 拼音匹配 → 表单草稿填充 → 人工确认提交"的完整链路。现需将这套逻辑泛化，推广到更多业务数据创建场景。

核心目标
  • 抽象统一框架：将制单的交互逻辑、匹配引擎、表单填充机制抽象为通用引擎，支持多种业务场景
  • 专属智能体隔离：每个业务场景对应独立智能体，独立打磨识别精准度，互不干扰
  • 可插拔扩展：新增业务场景只需配置智能体 + 定义表单模板 + 对接业务API，无需改动框架
  • 统一用户体验：所有场景共享一致的交互范式，降低用户学习成本
明确排除
  • 带库存校验执行逻辑的单据（如发货单），暂不在本引擎覆盖范围
  • 审批流、工作流等流程性逻辑，本引擎仅负责"创建"环节
02

核心架构设计

采用"统一交互框架 + 单表单专属智能体"的分层架构。框架层负责交互、路由、表单渲染；智能体层负责业务识别与匹配。两层通过标准化接口解耦。

关键设计决策
  • 为何不使用单一通用智能体？ 不同业务单据的字段结构、匹配逻辑、校验规则差异大，单一智能体难以兼顾精准度。专属智能体可独立优化Prompt和知识库
  • 为何框架层统一？ 交互范式（输入→识别→填充→确认）高度一致，统一框架避免重复开发，且用户体验一致
  • 拼音匹配引擎为何共享？ 客户名、产品名、供应商名等实体匹配逻辑相同，拼音索引是通用能力
03

覆盖范围与场景定义

引擎覆盖两类业务对象：输入型业务单据和基础业务主体。首批聚焦销售订单、采购单、报价单三个单据场景。

场景 类型 输入实体 输出对象 优先级 状态
智能制单 业务单据 客户 + 产品 销售订单 P0 已上线
智能采购单 业务单据 供应商 + 物料 采购订单 P0 Beta
智能报价单 业务单据 客户 + 产品 报价方案 P0 Beta
智能客户建档 业务主体 自然语言描述 客户档案 P1 规划中
智能销售机会 业务主体 线索描述 销售机会 P1 规划中
业务单据特征

包含主实体（客户/供应商）+ 明细行（产品/物料），字段结构化程度高，匹配逻辑以实体检索为主，输出为多行明细表格

业务主体特征

单一对象，字段以属性为主（名称、联系方式、地址、分类等），匹配逻辑以查重+补全为主，输出为扁平字段表单

04

统一交互逻辑

所有业务场景共享同一套交互流程，用户无需为不同场景学习不同操作方式。框架通过智能体路由器自动将用户输入分发到对应专属智能体。

统一交互流程
1
选择场景 / 自动识别

用户通过左侧导航切换智能体，或系统根据输入内容自动路由到对应智能体

2
多模态输入

支持语音、文本、图片、文件、剪贴板等多种输入方式，与智能体对话

3
智能体识别

专属智能体解析输入，提取业务实体（客户名、产品名、数量等），输出结构化数据

4
实体匹配

拼音匹配引擎将识别结果与系统已有数据匹配，返回候选列表供用户确认

5
表单草稿填充

匹配结果自动填充到对应场景的表单草稿，用户可逐字段确认或修改

6
人工确认提交

用户确认表单内容无误后，提交创建，调用业务API完成数据写入

页面布局规范

统一采用三栏布局：左侧智能体导航 → 中间表单草稿区 → 右侧智能体对话区。移动端自适应为单栏 + 底部对话抽屉。

05

专属智能体设计

每个业务场景对应一个专属智能体，独立部署在扣子(Coze)平台，拥有独立的Prompt、知识库和对话策略。智能体通过标准化输出协议与框架对接。

智能体标准化输出协议
// 智能体输出结构（所有智能体必须遵循） interface AgentOutput { agent_type: 'order' | 'purchase' | 'quote' | 'customer' | 'opportunity' entities: ExtractedEntity[] // 识别出的实体列表 raw_text: string // 原始输入文本 pinyin_map: Record<string, string> // 实体→拼音映射 confidence: number // 整体置信度 0-1 suggestions: string[] // 追问建议 } interface ExtractedEntity { role: 'subject' | 'detail' | 'meta' // 主体/明细/元数据 type: string // customer | product | supplier | material | ... name: string // 实体原始名称 pinyin: string // 拼音（用于匹配） attrs: Record<string, any> // 实体属性（数量、规格等） }
智能体 核心Prompt职责 知识库内容 输出实体
制单智能体 从自然语言中提取客户名、产品名、数量、规格 产品目录、客户简称映射 customer + products[]
采购智能体 从自然语言中提取供应商名、物料名、数量、规格 物料目录、供应商简称映射 supplier + materials[]
报价智能体 从自然语言中提取客户名、产品名、数量、价格偏好 产品目录、价格策略 customer + products[] + pricing
客户建档智能体 从自然语言中提取客户名称、联系方式、地址、行业 行业分类、区域编码 customer_profile
销售机会智能体 从线索描述中提取客户、预算、阶段、时间线 阶段定义、客户映射 opportunity
06

业务接口对接

框架通过适配器模式与各业务系统API对接。每个智能体对应一组业务API（查询匹配 + 提交创建），通过统一的适配器接口隔离差异。

适配器接口定义
// 业务适配器（每个场景实现一个） interface BusinessAdapter { agentType: string // 实体匹配：拼音 → 系统数据 matchEntities(entities: ExtractedEntity[]): Promise<MatchResult[]> // 表单模板：定义草稿区渲染结构 getFormTemplate(): FormTemplate // 数据校验：提交前校验 validateDraft(data: DraftData): ValidationResult // 提交创建：调用业务API submitDraft(data: DraftData): Promise<SubmitResult> }
智能体 匹配API 提交API 校验规则
制单智能体 客户拼音查询 + 产品拼音查询 POST /sales/orders 客户必填 + 至少1行产品
采购智能体 供应商拼音查询 + 物料拼音查询 POST /purchase/orders 供应商必填 + 至少1行物料
报价智能体 客户拼音查询 + 产品拼音查询 POST /sales/quotes 客户必填 + 至少1行产品 + 价格必填
客户建档智能体 客户查重（名称+电话） POST /crm/customers 名称必填 + 查重通过
销售机会智能体 客户拼音查询 POST /crm/opportunities 客户必填 + 预估金额必填
07

扩展新场景流程

新增一个业务场景只需4步，无需改动框架核心代码。整个流程以配置为主，开发为辅。

1
创建专属智能体

在扣子平台创建新智能体，编写Prompt定义实体提取规则，配置知识库，发布获取botId

2
定义表单模板

在框架中注册新场景的表单模板（JSON Schema），定义字段、布局、校验规则

3
实现业务适配器

实现 BusinessAdapter 接口，包括实体匹配、数据校验、提交创建三个方法

4
注册到路由器

在智能体路由器中注册新场景的配置项（名称、图标、颜色、botId、适配器），左侧导航自动出现新入口

注册配置示例
// 在 agentConfig 中新增一项即可 const agentConfig = { // ... 已有智能体 newScenario: { name: '智能XXX', desc: '场景描述', chatName: 'XXX智能体', icon: 'ri-xxx-line', color: 'blue', botId: '73428668****', quickActions: ['示例输入1', '示例输入2'], formTemplate: () => '表单HTML模板', adapter: new NewScenarioAdapter() } }
